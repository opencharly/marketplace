# /omarchy-eval:omarchy-pr-check

Evaluate an omacom/omarchy PR with charly checks on disposable beds. The
checks assert the resulting SYSTEM STATE (charly consequence checks),
not upstream's mocked call sequences — strictly stronger.

## The beds

- The stable golden chain (opencharly/eval-omarchy/charly.yml — the
  single source of config): `omarchy-vm` (ISO template) →
  `check-omarchy-eval-base` (provisions the VM and captures the golden
  snapshot) → `check-omarchy-eval-base-inst` (the INSTRUMENTED golden:
  charly, autologin, record tools incl. acpid, pr-apply, pre-seeded
  eval-head objects, warmed charly cache — captured as its own golden).
- Per-PR eval beds are ORACLE-GENERATED (by the config-oracle agent)
  into `pr-beds/pr-<N>/charly.yml` — never hand-edited,
  `charly box validate` gated. Each holds: the clone entity
  (`source.kind: clone`, `from_vm: check-omarchy-eval-base-inst`,
  `from_snapshot: golden`), the eval bed (`check-omarchy-pr-<N>-vm`)
  with the SINGLE pr-apply seam and record/spice evidence steps
  (terminal .cast + SPICE MJPEG → screen.mp4), and the RED-PROBE twin
  (`check-omarchy-pr-<N>-vm-probe`): SAME checks, NO apply — must FAIL
  on the golden (known-red).
- Eval runs on a linked-disk clone of the instrumented golden: NO
  --anchor, NO snapshot — the clone overlay dies with the run
  (`disposable: true`).
- The binding lane contract is opencharly/eval-omarchy
  `eval/PR-EVAL-LANE.md` (+ its `eval/references/*.md`): the 10
  standing rules, tier semantics, oracle marker/path rules, media
  contract and cold-reader rubric. Golden VM mechanics
  (provision/re-provision, delete-before-recapture, per-PR clones):
  `/charly-distros:omarchy-eval-golden`.

## The lane (pi-agent pipeline)

The lane runs ENTIRELY on pi agents — no GitHub Actions in the eval
path. The four agents are committed at opencharly/opencharly
`.pi/agents/omarchy-{config-oracle,eval-runner,eval-supervisor,cold-reader}.md`
(also published as the opencharly/pi-omarchy-eval package):

- config-oracle (TRIAGE + PLAN): class, channel, tier, clone entity,
  check plan with known-red justification, recording plan — authors
  `pr-plans/eval-plan-<N>.json` + `pr-beds/pr-<N>/charly.yml`. NEVER
  runs a bed.
- eval-runner (RED-PROBE → EVAL → EVIDENCE): runs beds as persistent
  background tasks; enforces orphan discipline, head-freshness
  preflight, golden re-provision duties. NEVER edits source.
- cold-reader: FRESH-context validation of the evidence packet against
  the rubric + the standing rules (pi vision AND deterministic
  evidence).
- eval-supervisor: ORCHESTRATION (lane board, slot arbitration,
  16-way concurrency), the REDO state machine, and the publication
  gate (comments post ONLY behind operator approval, rendered from the
  template).

## The procedure

0. Evaluate from the template: opencharly/eval-omarchy's
   eval/PR-EVAL-TEMPLATE.md — every report and posted comment is
   rendered from it and carries its EXTERNAL, NON-AUTHORITATIVE
   (by opencharly.ai) disclaimer verbatim. Pick the CHANNEL base the PR
   targets: dev = source-checkout lane (PR head in ~/omarchy);
   edge/rc/stable = package-level lane; rc = the release-validation
   flow (channel-set + update + migrations).
1. Load the rubric: omarchy's agents/skills (acceptance-tests,
   visual-verification, migrations, shell-dev, install-scripts,
   command-metadata, icon-font, hyprland, capture) — vendored and
   pinned at a quattro hash so evaluation criteria are version-locked.
2. Tier 0: classify the diff (the venue-ladder map) and assign a venue;
   extract the PR's "## Verification" claim; hardware-bound classes get
   PARTIAL/NOT-EVALUABLE, never a faked bed.
3. Apply the PR at the channel's seam (the apply contract): fetch
   pull/<N>/head SHA-pinned, install ONLY the changed files over the
   installed tree (dev lane: check out the PR head in ~/omarchy), and
   prove application with a pr-applied check — the known-red fixture
   surfaces a missed apply per-check. In the beds the apply lands
   through the single pr-apply seam
   (`pr-apply <N> <sha> <paths...>`).
4. RED-PROBE FIRST: run the twin bed (`check-omarchy-pr-<N>-vm-probe`)
   — same checks, NO apply — it MUST FAIL on the golden. A green probe
   means the check is not known-red or the golden is stale: STOP, never
   eval on a green probe.
5. Eval: `charly check run check-omarchy-pr-<N>-vm` on the linked-disk
   clone from the instrumented golden (oracle-generated in
   pr-beds/pr-<N>/charly.yml); the plan drives the PR-behavior check
   plus the record/spice evidence steps (terminal .cast, SPICE MJPEG →
   screen.mp4) visible in the desktop recording frames.
6. Head-freshness every run: compare the plan's headSha with the LIVE PR
   head (`gh api repos/omacom/omarchy/pulls/<N> .head.sha`) — a
   force-pushed upstream head orphans the pinned head and pr-apply
   fails; on mismatch STOP and regenerate the bed.
7. Evidence contract: the check-run summary.yml + the .cast + the video
   artifact + the ADE verdict (charly check feature run --agent) where
   the class requires visual grading.
8. Render the validation comment from eval/PR-EVAL-TEMPLATE.md; POST
   only behind the operator approval gate.
9. Batch loop: repeated bed runs, one per PR, with the SHA-keyed result
   cache (eval-omarchy's scripts/omarchy-rollup.py) skipping unchanged
   heads.

## Update-channel machinery (channel-class PRs)

- `omarchy-channel-set <ch>` round-trips (get/set; re-set the same
  channel is a no-op).
- Updates run pending migrations per channel (the S5 harness is the
  per-channel variant); the stable mirror runs one month behind —
  assert tracking, not a version string.
- The pacman guard: a bare `pacman -Syu` / `yay -Syu` is stopped and
  pointed at `omarchy update` (one-transaction bypass exists).
- The dev channel binds the OS to a git checkout in ~/omarchy: apply
  PRs there by checking out the PR head and updating.
- A channel re-provision bakes the current channel state + pre-seeded
  eval-head set into the instrumented golden (see
  omarchy-eval-golden).

## Guardrails (from doctrine)

- Never let an ADE/iteration loop rewrite widget QML wholesale
  (shell-dev.md glyph loss).
- Migrations double-run (the S5 harness proves idempotence).
- Assert the SERVES not the RUNS (quickshell: ping reads responses;
  a supervisor uptime can pass on a wait wrapper).
- PR-body claims are claims, not facts.
- A RED-PROBE that passes is a PROCESS finding, never a green light.
- A failed eval bed is left running BY DESIGN for debugging — destroy
  and confirm domstate gone before the next run on the same clone disk.
