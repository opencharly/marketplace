# 2026.229.1115 — three CHANGELOG H1s disagree with their filenames; the newest is mine

`CHANGELOG/2026.229.1052.md` landed on `main` at `8ea7eeb4` carrying the H1
`# 2026.229.1023`, and its closing line still reading `Placeholder CalVer — the
pr-validator finalizes it at merge`. Both are repaired here.

Sweeping the rest of `CHANGELOG/` for the same shape found **two more, already on
`main`** — so this is a recurring class, not a single slip:

| entry | H1 said | merged |
|---|---|---|
| `2026.203.1037.md` | `2026.203.1099` | 2026-07-22 |
| `2026.225.1226.md` | `2026.999.9999` — a raw placeholder | 2026-08-13 |
| `2026.229.1052.md` | `2026.229.1023` | 2026-08-17 |

All three are repaired here (R3: the fix covers every surface it applies to). In
each case the FILENAME is authoritative and the H1 is simply wrong — `v2026.203.1037`,
`v2026.225.1226` and `v2026.229.1052` all exist as tags, and no tag exists for any
of the three H1 CalVers. Three different validator sessions across four weeks hit
the same shape, which is what makes a mechanical check the fix rather than more care.

**The sweep that found them needed two attempts, and the first was worse than
useless.** Anchored on `# <calver> — <title>`, it reported 37 of 200 entries
divergent — every false positive an older entry using a different H1 convention.
A search anchor encodes an assumption about the FORM of what you seek; the
corrected instrument classifies into *matching CalVer* (172), *no CalVer in the
H1 at all* (25, an older convention and not this defect) and *a DIFFERENT CalVer*
(3, the real set). An instrument's output is not evidence until the instrument is
shown to discriminate.

## Root cause

The `pr-validator` finalizing `plugins#190` ran `git mv` to rename the placeholder
entry, then rewrote the H1 and the placeholder line **in the working tree**, then
committed with `git commit -F -` and no `-a`. `git mv` stages a rename; a
subsequent edit to the renamed file is a separate, unstaged change. The commit
therefore captured the rename and none of the content.

Git said so. `git status --short` printed:

```
RM CHANGELOG/2026.229.1023.md -> CHANGELOG/2026.229.1052.md
```

`R` is the staged rename; `M` in the second column is the unstaged modification.
The validator read that line as confirmation the rename and the edit were both
ready, when its second character was the warning that they were not.

## The check that would have caught it, and why the one performed did not

The finalization self-verified with `head -1 CHANGELOG/2026.229.1052.md` — which
reads the **working tree**, the one place the edit did exist. Every artifact that
would actually ship — the index, the commit, the merge — still held the old H1.
An assertion aimed at the object you edited rather than the object you are about
to ship cannot fail, however carefully it is written.

The verification is `git show :<path>` for the index, or `git show <sha>:<path>`
for a commit, never a bare read of the file. This is the same rule the evidence
reference states for pushed branches and published artifacts, applied one level
in: **read back the artifact, not the intent.**

## Why it survived to `main`

The post-merge trailer check passed and was allowed to stand in for a tree check.
It verified the merge commit's *message* against the expected attribution, which
was correct, and asserted nothing about the merge commit's *contents*. A gate that
is green on the half you did not break is not evidence about the half you did.
