# 2026.215.9999 — `git add` is all-or-nothing: consolidate the stale-pathspec guard

A single `git add` whose pathspec includes a path that no longer exists fails the **whole** add —
`fatal: pathspec '<old>' did not match any files`, exit 128, nothing staged, including every path
that did resolve. Two shapes hit it, both silent because a prior command already staged something,
so the failed `add` leaves `git status` looking exactly as intended:

| Shape | What already staged it | What lands |
|---|---|---|
| deletion, old path still named | the deletion was pre-staged | only the deletion — a partial commit |
| rename + content edit | `git mv old new` staged the rename | the rename, with the edit dropped |

## What actually changed here, and why the first draft was wrong

**A guard for this already existed.** `references/validator-and-calver.md` has carried it since
`218e43e` (2026-08-03 10:24), and `internals/agents/pr-validator.md`'s Phase 3 carries the
equivalent procedural self-verify. The first draft of this entry called today's incident "the third
occurrence" and framed the fix as *a missing rule*. Both are wrong, and a fresh evaluator caught it.

Per `CHANGELOG/2026.197.1925.md` (Member 5), the rename shape alone had **already recurred three
times** — `charly` PR #131, `pkg-arch` PR #4, and the evaluator finalizing `plugins` PR #75 — each
caught pre-push, and caught *only* because the prescribed `git show HEAD:<new> | head -1`
self-verify was actually run. Today's `opencharly/docs` #5 is the **fourth**, and the first to
**land**: the file merged to `main` correctly named `CHANGELOG/2026.215.1609.md` with its heading
still reading `# 2026.215.9999 — …` (fixed by `docs` #6).

So the real root cause is not an absent rule. It is that the guard lived **only in the
CalVer-finalization flow** — a reference file and an agent checklist — while the mechanism applies
to *any* commit that renames or deletes a file, and its remediation was an **extra command you have
to remember to run**. A general committer doing a rename+edit had no reason to look there.

## The change

Consolidated to one owner rather than adding a third description (R3):

- `internals/skills/git-workflow/SKILL.md` — the general invariant, next to the
  "Post-commit staging verification" bullet it amends: both shapes, the correct staging, and the
  tells.
- `references/validator-and-calver.md` — trimmed from a second full explanation to this flow's
  *instance*, cross-referencing the invariant and keeping the flow-specific `head -1` verify.
- `internals/agents/pr-validator.md` — untouched; its Phase 3 steps are an agent's operational
  checklist, not a restatement of the mechanism.

## Why it needed stating outside that flow at all

The pre-existing "Post-commit staging verification" invariant tells the reader to confirm every
intended file is listed in `git show --stat`. **The rename shape passes that check.** Reproduced in
a scratch repo:

```
$ git mv old.md new.md && printf '# 1609 heading\n' > new.md
$ git add old.md new.md
fatal: pathspec 'old.md' did not match any files      # exit 128 — nothing added
$ git status --short
RM old.md -> new.md                                    # looks exactly as expected
$ git commit -m x                                      # succeeds
$ git show --stat
 old.md => new.md | 0                                  # the file IS listed
$ git show HEAD:new.md | head -1
# 9999 heading                                         # the edit was dropped
$ git status --short
 M new.md                                              # the edit, still unstaged
```

Presence in `--stat` is not the signal. The tells are the **magnitude** — `| 0` insertions on a
commit meant to change content — and the **leftover ` M <new>`**. Both appear in commands already
run after every commit, which is the point: the guard no longer depends on remembering an extra one.
