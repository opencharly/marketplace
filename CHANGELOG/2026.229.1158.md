## 3. The Debian-family `distro:` trap

`/charly-internals:vm-spec` gained the omission trap: on a Debian-family cloud image, leaving
`source.distro` unset rendered `openssh` plus `systemctl enable --now sshd` — a unit Debian and
Ubuntu do not have — and with cloud-init's deliberate `mask ssh.socket` that left a
socket-activated sshd masked and never started. The guest booted fully and served nothing.

## Why this is a narrow file set, not a wholesale regeneration

Worth recording, because the first attempt was wrong in a way that looked right. Running
`charly marketplace generate` wholesale produced **21** modified files, and the extra 16 were not
drift to tidy up — they were **reverts**. Regeneration wanted to delete ~500 lines of prose that
had legitimately landed here, including 317 lines from
`git-workflow/references/evidence-and-freshness.md` and 107 from `agents/pr-validator.md`.

The cause is the projection ordering this repo works under: **a projection merges before the
superproject source that pins it.** So prose can be correct and landed *here* while its candy
source is still in flight on a superproject branch. Regenerating from a superproject tree that
lacks that pending source does not "bring the projection up to date" — it drags it backwards, and
the diff gives no hint, because a reverted projection looks exactly like a projection that was
never stale.

The fix is scope, not tooling: this change keeps only the projections of the candy files it
actually edited, and every deleted line across those files is one it deliberately replaced.

## Known-stale, stated rather than quietly shipped

Six corrections are landed in their candy sources but are **not** in this projection, because
regeneration is currently impossible: in the superproject tree that owns these sources, both
`charly marketplace generate` and `charly docs generate` exit 1 — the pinned `distro-arch` and
`distro-fedora` copies fail the new `source.distro` validation, and every project-loading command
dies on it. Until those two repos land and the pins bump, this projection carries:

- a `TemplateFuncs` list naming 6 functions where there are 12 (`anyRepoHasURL`, `hasSuffix`,
  `join`, `printf`, `replace`, `shquote` omitted) — the six came from a windowed grep;
- authoring gotchas ordered `11, 13, 14, 12`, which breaks gotcha 11's by-number cross-reference;
- a `sudo`-redirect example in one `yaml` fence whose five sibling `command:` keys make a
  permissive `yaml.safe_load` keep only the last and silently discard both wrong examples;
- `effectiveDistro` prose in `internals/skills/vm-spec/SKILL.md`,
  `internals/skills/cloud-init-renderer/SKILL.md` and `vm/skills/vms-catalog/SKILL.md`, describing
  a `base_user`-based distro inference this cutover deletes, and a five-id distro vocabulary that is
  now thirteen;
- **the most consequential one:** `internals/skills/vm-spec/SKILL.md` tells the reader the sshd
  start "falls back to the other unit name, so omitting it costs a redundant `systemctl` call
  **rather than an unreachable VM**". That is false against BOTH code states, by two different
  mechanisms — on `sdk@origin/main` `sshUnitForDistro` switches
  `{"debian","ubuntu" → "ssh"; default → "sshd"}`, so an omitted `distro:` yields `sshd`, the wrong
  unit for a Debian-family guest; on this cutover's sdk leg it is
  `return spec.DistroSSHUnits[distro]`, a bare map lookup yielding `""`. It also contradicts its own
  paragraph's opening ("boots unreachable"). It is worse in kind than the others: they make a reader
  over-cautious, this one makes them confident about the exact omission the paragraph exists to warn
  against, in the closing sentence where the takeaway sits;
- two jammed headings in `check/skills/check/references/authoring-gotchas.md`, and one orphaned
  lead-in in `internals/skills/vm-spec/SKILL.md` where "authored as:" sits ~30 lines from the yaml
  example it introduces.

All six are fixed in the candy sources on the superproject branch (unmerged). They are named
here because a projection that is known-stale and silent is worse than one that says so, and because the reader
who hits the 6-of-12 list needs to know the source is already right.

`vm`'s projection is deferred for the same class of reason, so the firmware-matrix correction lives
in its candy source until a tree with every source regenerates it.
