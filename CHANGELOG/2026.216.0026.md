# 2026.216.0026 — tutorial-shell composes two candies; the init is injected

The `/charly-distros:tutorial-shell` card listed three candies including `supervisord`, with a
"Why these three candies" section calling it "the container init that actually runs the service".

That describes composing the init by hand — which the init auto-injection (`opencharly/sdk` #119)
makes unnecessary and, done as a `require:`, actively wrong: `require:` is target-blind and would
drag supervisord onto systemd machine venues that already have an init. The card now lists
`ripgrep` and `sshd` and explains why the init is absent: `sshd` declares a service, so charly
resolves the init the target needs and injects it — supervisord for a container image, nothing
extra for a machine venue.

## Why this moved now rather than in a later skills pass

This `SKILL.md` is a **source** of `recipes/distros/tutorial-shell.md`, a page regenerated inside
`opencharly/docs` #8. Left alone, the published site contradicted itself on its own flagship
example: the generated box page saying *"two candies, the init is deliberately absent"* directly
beside the generated recipe card saying *"three candies, supervisord"*.

That is one diff, not two repositories — which is what a docs validator caught, and what corrects
the earlier decision to defer every skill update until after the code landed. The general rule
still holds (a skill describes the fixed state, so it follows the fix); the exception is a skill
that is itself a source of the documentation being changed, which has to move with it.

## A second stale claim, same mechanism

`core/skills/service/SKILL.md:101` stated that `charly box validate` **enforces** that an image
with an init-system layer must include the required dependency layer. That enforcement was
DELETED in the #119 plugins leg (`validateInitDependencies` in `candy/plugin-box/validate_graph.go`
— a whole-tree grep now returns zero hits), so the skill had been telling readers that validate
polices something it no longer does.

The line now describes what actually happens: the dependency layer is **injected, not policed**.
A box composing a `service:` candy gets the active init's `depends_candy` added to its composition
automatically, so it never has to list `supervisord` by hand and can no longer be missing it.

This is not a cosmetic wording fix. Every skill in this repository is published to opencharly.ai,
so a false enforcement claim is a false claim on a public surface — about the exact mechanism this
chain changes. R2 forbids parking it for a later docs batch.

## Land order

After `opencharly/sdk` #119 (the injection), `opencharly/sdk` #120 (which fixes #119's incomplete
half — the injected candy now reaches the collectors, restoring the acceptance probes it had
silently removed), and `opencharly/distro-fedora` #11 (the box), so neither claim describes a
behaviour that is not yet true.
