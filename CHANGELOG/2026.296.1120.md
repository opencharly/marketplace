# 2026.296.1120 — fix(refresh): say the pin count without the number, and forbid the count

## Summary

Head `5379dd6f19131cbba62324e078b0b89ab23ef697`, **4 files, +260 −15** — the refresh workflow no
longer states the refs list's size as a literal, the workflow's own harness forbids the class, and
the body's own headline count of the diff is now checked against the diff.

**The finding.** The validator's review of the last refresh PR (`opencharly/marketplace#534`)
carried this note: *"the body says '200 pin(s) advanced' but also says 'removes it for the
remaining 176'... That is a possible inconsistency"*, and *"The number 176 is likely a hardcoded
template string that's now stale."* That PR passed. The note is not filed away: it is fixed here,
and the class it names is closed with it.

**The mechanism.** The string lives in the refresh workflow's PR-body template, and the template
carried it from the day the workflow was written, when the refs list had that many entries. The
list has since grown and changes on every refresh, so a hand-written count in the template is
false the moment the next refresh lands. The same file carried three more of the same kind: the
count of the generator's per-ref progress lines in the comment that justifies the log elision, the
size of that log in the same comment, and the size of the refs list in the workflow's own header.
The two counts in the file did not even agree with each other — one said how many pins the list
held, the other how many progress lines a full refresh prints — which is what made the pair read
as a contradiction. The count the body legitimately reports — how many pins a run advanced — is
DERIVED from the resolver's own summary line, and is untouched.

**The fix: say it without the number.** The claim each paragraph is actually making survives it —
the pins are hand-maintained, and hand-maintained pins go stale silently.

| site | before | after |
|---|---|---|
| the workflow's header | `176 hand-maintained pins` | `a refs list of hand-maintained pins` |
| the PR body template | `this workflow removes it for the remaining 176` | `this workflow removes it for the rest of them` |
| the log-elision comment | `641 of them on a full refresh` | `one per ref on a full refresh` |
| the log-elision comment's size | `one per ref on a full refresh, ~44 KB of them` | `one per ref on a full refresh` |

**The guard.** `scripts/refresh_publish_test.sh` — the harness that already extracts the
workflow's blocks and runs them — now asserts that the refs list's size is stated without a
number: a count of pins or of refs, of the refs left over, or of the per-ref progress lines. The
CLASS, not the instance: a later list cannot re-introduce the drift under a different number. The
assertion is checked twice — against the workflow's source, and against the body the workflow
ASSEMBLES (the artifact boundary, so the template's own emitted text is what is judged).

**Round 1 — the validator's review, read in full.** The verdict was **PASS**, and it raised three
observations. All three are fixed in the second commit:

1. *The guard matched `pins?` but not `refs?`, while this body's own R1 sweep greps for a count of
   `pins?` OR `refs?`* — so a count phrased as "N refs" would have walked through the very hole
   the sweep looks for. The pattern now covers both nouns, and the guard's comment says why the
   two must agree. The widened alternative is proven non-vacuous below: a source comment and an
   assembled-body line that each state "176 refs" turn the harness RED.
2. *The retained `~44 KB of them` is a hand-written figure that scales with the refs count.* It is
   gone — a byte size that drifts with the list is the same defect as a count that drifts.
3. *The prose "the same count in the workflow's own header" was loose* — the header and the log
   comment carried two different counts. This body now states what the two figures were.

**Round 2 — the validator's BLOCK, read in full, and its root cause.** The verdict was **BLOCK**
on one thing: the body's own headline diffstat. The body at that head said "2 files, +33 −8"; the diff was
"2 files, +32 −5". The RCA, in full, in the round's comment on this PR:

- **The mechanism.** The headline is a HAND-WRITTEN count of the change's own size. The body is
  rewritten for every new head — the sha, the prose, the evidence — and the number is the part
  that gets forgotten: this PR's second commit changed the line totals (`refresh.yml` +1/−1, the
  harness +6/−4) and the headline kept the first commit's numbers. It is the same drift this PR
  exists to remove from the workflow's body template, one level up: a count of a tree, recorded
  once, that is false the moment the tree changes.
- **The missed control.** `scripts/pr_body_lint.py` is the mechanical half of the pre-validator
  self-audit, and its own docstring says a body-only BLOCK is an ORCHESTRATOR VALIDATION
  FAILURE — a verdict spent on something a deterministic check could have caught. It checked the
  sections, the footer, the rules, the claims, the pasted head, and a count stated against a
  table the body PASTES. It had no rule for a count stated against the DIFF. The `head` family
  already reaches the repository (`--head` / `--repo`), so the machinery was there; the rule was
  missing.
- **The root fix.** A new `diffstat` family in the same linter: the diffstat the body's HEADLINE
  states — "2 files, +33 −8", and git's own "2 files changed, 33 insertions(+), 8 deletions(-)" —
  must equal the diff's own totals, read with `git diff --numstat` against the base. The scope is
  the paragraph that carries the pasted `Head` sha, because that paragraph is the body's
  statement about THIS commit: a diffstat quoted about ANOTHER diff, in another paragraph, is
  left alone, and a diffstat inside a fenced block is pasted evidence, not a claim. When the diff
  cannot be read the rule SKIPS, visibly, rather than guessing. The rule is proven able to fail
  below, by a mutation that turns exactly three tests RED.

**The predecessor.** This is the successor to `opencharly/marketplace#534`, whose validator review
carried the finding this change fixes; #534 gets its `RESOLVED — superseded` record, and it is
closed. The issue that owns the defect's record is `opencharly/marketplace#547` — claimed and
assigned in this repo before this branch was opened.

Closes #547
