# 2026.277.1911 — fix(ci): stop refresh.yml assembling a PR body over GitHub's 65536-byte limit

## Summary

The daily refresh **could not open its PR**: the body it assembles exceeded GitHub's
65,536-byte ceiling, so `gh pr create` was rejected. The rejection is
**deterministic**, and the retry loop beneath it retried that deterministic error
three times with sleeps — so the run died with an opaque GraphQL error that reads
like a transient 5xx, while the refreshed branch sat pushed and the corpus silently
stopped tracking its tags.

**Cause: one unbounded emitter.** `cat /tmp/generate.log` at
`.github/workflows/refresh.yml:226` pasted the generator's entire output — 62 KB of
the body. Its composition, on the real log from the failed run:

| line shape | count | why it was in the body |
|---|---|---|
| `Downloading <ref>...` | 641 | routine per-ref progress, already listed by the refs-resolution section and the changed-file list |
| generated artifact paths | 470 | the file list, already listed by `git status --porcelain` |
| warnings / errors | 0 | — |

**The fix preserves the code's stated intent.** The comment it replaces reads
*"Paste the WHOLE generator log, not a tail: a warning earlier in the file must be
visible in the body that asserts the tier."* That reasoning is sound — a `tail`
could drop exactly the warning the section exists to surface — so a tail is still
not what this does. The routine `^Downloading ` progress lines are elided; every
other line is emitted verbatim; and the elision is announced with exact counts plus
where the complete log lives. A second hunk asserts the assembled body's byte size
after the push and before `gh pr create`, so an over-long body fails in one line
with its byte count instead of three opaque retries. It sits **after** the push
because the existing order deliberately pushes first, so a failure costs a PR
rather than the night's refresh.

The diff is one file: `.github/workflows/refresh.yml`, `+43/-4`. It touches no
generated corpus file, no refs-list pin, and no other workflow.

**1. The defect, reproduced.** The unmodified block fed those logs:

```
$ bash run.sh block-OLD.sh body-OLD.md
  === OLD body: 70876 bytes (limit 65536) ===
```

That is 5,340 bytes over, which is why the run failed. The CI failure it reproduces,
verbatim from run `37226249924`:

```
pull request create failed: GraphQL: Body is too long (maximum is 65536 characters) (createPullRequest)
pull request create failed: GraphQL: Body is too long (maximum is 65536 characters) (createPullRequest)
pull request create failed: GraphQL: Body is too long (maximum is 65536 characters) (createPullRequest)
```

Three attempts, 19:02:59 / 19:03:10 / 19:03:31 — a deterministic rejection retried.

**2. The fix, on the same logs.**

```
$ bash run.sh block-COMMITTED.sh body-COMMITTED.md
  OLD body: 70876 bytes   (OVER the 65536 limit -> gh pr create rejected)
  NEW body: 27148 bytes   (under, margin 38388 bytes)
```

**3. The property that matters — nothing but progress lines is dropped.** This is the
check that makes the elision safe rather than a size trick: every non-`Downloading`
line of the generator log must survive into the new body.

```
$ wc -l < generate.log
1111
$ grep -c '^Downloading ' generate.log
641
$ grep -v '^Downloading ' generate.log > nonprog.txt
$ for f in body-OLD.md body-COMMITTED.md; do echo "  $f : $(grep -Fxv -f "$f" nonprog.txt | wc -l) MISSING"; done
  body-OLD.md : 0 MISSING
  body-COMMITTED.md : 0 MISSING
$ grep -c '^Downloading ' body-COMMITTED.md
0
$ grep -m1 'Elision notice' body-COMMITTED.md
> **Elision notice — read this before quoting the block above.** `641` of
```

All 470 non-progress lines survive; the 641 progress lines are gone; and the notice
states the true counts (`641` of `1111`).

**4. Both files still parse.**
