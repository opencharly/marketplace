# 2026.230.0406 — the two published guards become runnable

Projection of `opencharly/charly#289` at `2edccfd4`. One page, `+7/-4`.

The section titled *"A guard that cannot fail is worse than no guard"* shipped two guards that could
not run. `<entry>` and `<superproject-path>` read as placeholders and are **shell redirections**:
bash parses `CHANGELOG/<entry>.md` as `CHANGELOG/` with stdin from a file named `entry` and stdout
to `.md`.

**They do not fail silently — they fail on stderr, and the structure discards it.** stdout is empty,
and a `for sha in $(…)` loop consumes stdout, so the loop body never runs and the caller sees *no
SHAs found* — a clean pass. The stray `.md` is conditional: redirections are performed left to
right, so `< entry` fails first and `> .md` is only reached when a file named `entry` exists.

**Repairing the syntax was not enough.** Executed, guard 1 found four SHAs and resolved **none** —
`1ba91da1` is a `docs` commit and `c4aa2219` a `plugins` commit, and the repo list reached neither.
That is the vacuity the paragraph beneath it describes, with the repos swapped. The list now derives
from `.gitmodules` and the output names the repo that resolved each sha.

Found by executing the page, which nobody had done. **Prose review cannot execute**, so a published
command is unverified by construction until someone runs it.
