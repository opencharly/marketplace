# 2026.230.0406 — the guard becomes able to fail

Projection of `opencharly/charly#289` at `326852cf`. One page, **`+24/-5`** against `plugins/main`.

The section titled *"A guard that cannot fail is worse than no guard"* published two guards that
could not run, and two successive fixes each left it unable to fail in a different way.

**`<entry>` and `<superproject-path>` are shell redirections, not placeholders.** Bash parses
`CHANGELOG/<entry>.md` as `CHANGELOG/` with stdin from a file `entry` and stdout to `.md`. The error
goes to **stderr** while stdout stays empty, and a `for sha in $(…)` loop consumes stdout — so the
loop body never runs and the caller reads *no SHAs found* as clean. **That is the empty-set defect,
not silence: the error was printed and the construction discarded it.**

**The first fix failed more quietly than the bug.** `git config -f .gitmodules` reads from the cwd,
and only the superproject has one — from inside `plugins` it exits 1 with **empty stdout and empty
stderr**, the repo list collapses to `.`, and the guard prints a confident all-`LANDED` table.

**The second fix left `|| continue` as the only miss path.** A SHA resolving in no repo **vanished**
from the table and the run still exited 0. **A populated table reads as a working check where an
empty one might prompt a second look** — the output's appearance improved while the defect stayed.

Now every failure mode refuses instead of narrowing: an unresolvable SHA prints `UNRESOLVED`, the
run exits nonzero on `UNRESOLVED` or `UNMERGED`, `$entry` is existence-checked, and the repo list
refuses when empty. The root is resolved rather than assumed, and every path is absolute.

**The published default names an entry that exists on `main` and cites three SHAs**, so a reader
running it verbatim gets rows rather than silence. Executed from the superproject and two
submodules: identical output, one `UNRESOLVED`, one `LANDED`, exit 1.
