# 2026.241.1715 — fix: the refresh survives a transient GitHub API failure

## Summary of changes

The second real refresh run produced its branch and content correctly — 176 pins read, 40 advanced,
corpus regenerated, branch pushed — and then hit:

```
HTTP 504: We couldn't respond to your request in time. … Please try resubmitting your request
```

Losing a whole refresh to a 5xx that **GitHub itself tells you to resubmit** is a robustness gap.

**The previous failure in this step is fixed and stayed fixed:** the "not permitted to create or
approve pull requests" error is **absent** from this run — the bot token from `#246` worked. This is
a different, transient failure.

## Why not a plain retry loop

A bare `for i in 1 2 3; do gh pr create …; done` would be wrong twice over:

- **a 504 can mean the write SUCCEEDED** and only the response timed out — a blind retry then fails
  with "already exists" and turns a success into a red run;
- **retrying a genuine permission error** three times helps nobody and buries the real cause under
  two more identical failures.

So after any failed attempt it **asks whether the PR now exists for the branch**. If it does, that
is success. Otherwise it retries a bounded three times with a short backoff, then fails with the
branch name, the recovery URL, and the reminder **not** to "fix" a permission error by enabling
`can_approve_pull_request_reviews`.

The push-before-PR ordering that made the 504 survivable is unchanged — it is exactly why the failed
run's branch was intact enough to open by hand as **`#247`**.
