**Edge 1 — an EMPTY answer value is refused.** A body whose `## Change classification` carries the key and nothing after it used to pass the rule at 0 findings. The merged changelog then holds a cutover marker beside an answer that says nothing — as unresolvable as no answer at all. The rule now refuses the empty value, and it refuses it as SILENCE (its own finding says the value is empty), not as a `none`: the two are different defects and the reader of the finding has to be able to tell them apart.

**Edge 2 — the inapplicable skip is VISIBLE.** The rule prints a NOTICE when the subject cannot be READ (`--repo` and `--head` supplied, the read fails). When either is ABSENT the rule never runs — and printed nothing, so a caller that forgot `--repo` could not tell *"the body is fine"* from *"the rule never looked"*. The rule's own docstring says the rule *"SKIPS, visibly"*, which was true of the failed read and too broad of the inapplicable case. It now prints a NOTICE for the inapplicable case too, and the NOTICE says plainly that the rule was SKIPPED and why.

**Edge 3 — the key anchor reads the org's own key.** `BREAKING_ANSWER` matched `^\s*(?:[-*+]\s+)?\**\s*breaking change\b` and then took the value after the first colon in the rest of the line, so a line opening `**Breaking change policy:** …` read as an answer — a false positive waiting to happen inside `## Change classification`. The anchor is now the WHOLE published key, `**Breaking change + rollback:**`, so a different key is not an answer.

**The review's non-blocking nit is answered in this second commit.** The validator read the NOTICE's wording as imprecise: it says *"no `--repo` was given"*, and the nit observed that the branch *"also fires when `--repo` is present and `--head` is absent"*. It does not: the head is DERIVED from the repository when `--head` is absent, so `repo and head` holds whenever `--repo` is given, and the branch is reached only when `--repo` is absent — the wording was exact. It is now exact BY CONSTRUCTION as well: the NOTICE names the argument the branch's own condition found missing, so it cannot go stale if the head's derivation ever changes, and the case the nit says is uncovered IS covered — a new test gives `--repo` and no `--head` and asserts that the rule RAN (the bang finding fires and no skip is announced).

**The validator's PASS then found the arm that promise was resting on was DEAD CODE, and this third commit brings it to life.** The second commit's NOTICE named the missing argument *by construction* — and the construction had a hole: the head was derived with `git rev-parse HEAD` under `check=True`, so a repository whose HEAD cannot be read (a path that is not a git repository, or a repository with an UNBORN head) raised and killed the linter with a Python traceback. The only way to reach the NOTICE's `--head` arm with a repository given was therefore the very call that crashed first: the arm promised a name the tool could never print. The derivation now FAILS LOUDLY BUT GRACEFULLY — a failed read leaves the head unset instead of raising — so the NOTICE is reached and names `--head`, which is the argument that is genuinely missing. A new test exercises exactly that case and is RED against the previous commit: it ERRORS on the very traceback this commit removes.

**The branch's own comment contradicted the code beside it, and it is corrected here.** The NOTICE branch carried the sentence *"this branch is reached only when `--repo` is absent, and the name it prints is `--repo`"* — true when round 2 was written, and FALSE once the derivation stopped raising. A comment that contradicts the code next to it is a doc divergence, so it is corrected in this same commit: the branch is reached two ways, and each names the argument it really lacked — `--repo` absent (there was nothing to read a head from), and `--repo` given but its HEAD unreadable (the caller gave the repository and did not give the head).

**The validator's second minor is FIXED, not filed away.** The test helpers created their temporary directories with `tempfile.mkdtemp` and never removed them. Every temporary directory now goes through ONE module-level helper that registers its removal with the test case, so all five sites are collected when the test ends — the two that pre-date this change and the three this change adds. The file's convention is one mechanism now, not five copies of the same line.

## Change classification

**Breaking change + rollback:** the org-wide body linter now refuses two bodies it accepted before. A body whose `## Change classification` carries `**Breaking change + rollback:**` and NOTHING after it — an empty value — now fails the rule, where it passed. And a body whose answer line opens a DIFFERENT key (`**Breaking change policy:** …`) with a reasoned value now fails too, where it passed: a different key is not an answer, so the body has no answer at all. Every opencharly repo that runs this linter — the umbrella's pre-push gate runs it over `marketplace/scripts/pr_body_lint.py` — sees those bodies refused at the push. The rule's home already said so (opencharly/opencharly#805): the line must CARRY AN ANSWER. Two quieter changes ride with them: the inapplicable skip now PRINTS a NOTICE instead of printing nothing, so a caller that forgot `--repo` can see that the rule never looked; and a `--repo` whose HEAD cannot be read is now ANNOUNCED (`no --head was given … the bang rule is SKIPPED`) and returns 0, where it used to die on a Python traceback and return 1 — a caller that pointed `--repo` at a non-repository, or at a repository with an unborn HEAD, saw a crash where it now sees the tool's own voice. Rollback is this change's revert: the three edges, the eight cases, the NOTICE's named argument and the graceful derivation land together and leave together, and the linter's behaviour returns to accepting an empty value, reading a loose key, skipping silently and crashing on an unreadable head.
