# 2026.216.2340 — the encrypted-volume boot gate is a capability, not a backend name

The `enc` skill's boot section was a table headed **Boot Behavior: Backend-Gated**, which taught
autostart as something a deploy earned by picking the right credential store — a row per backend,
with the backend name as the gate.

The section now leads with the arrangement encrypted deploys get out of the box, and gives the
reason as a capability rather than a backend list:

> Can the passphrase be obtained with no human present?

Secret Service can — it becomes readable when the keyring unlocks at login, without anyone typing a
passphrase for the volume. So an encrypted deploy backed by it carries `WantedBy=default.target` and
`TimeoutStartSec=0`, and `ExecStartPre` blocks in the mount until the keyring opens rather than
timing out. That is the out-of-the-box arrangement: `secret_backend` resolves to the keyring by
default, so nothing needs configuring to get it.

Secret Service satisfying the capability is a consequence, not the definition — the skill no longer
enumerates backend names as the gate, and `ResolveEncPassphraseForMountWithResolver`'s
`usesWaitingBackend` predicate is cited as where the code expresses the same split.

The other outcome is still documented, because it is a supported configuration and an operator will
hit it — but as a consequence of the same capability, not as a row in a backend matrix. A deploy
whose passphrase cannot be obtained without a person gets no `WantedBy=` target, so nothing pulls it
in at boot; it is simply absent afterwards, with no failed unit to look at, and `charly start` is
what brings it up. That last detail is the one an operator actually needs: the failure mode is
silence, not an error.

No backend is named in either direction, and nothing is described as removed, unsupported, or
deprecated.

The section is renamed to **Boot Behavior: Waiting for an Unattended Unlock**, and the one
cross-reference to the old heading moved with it.

## The sweep found a second, larger problem in the same file

Sweeping for other statements of the removed model turned up something else: the `enc` skill's
source map described a file that does not exist. `charly/enc.go` was cited eight times, and every
symbol attributed to it — `encMount`, `encUnmount`, `encPasswd`, `ensureEncryptedMounts`,
`encPlanFor`, `encStatus`, `encryptedPlainDir`, `isEncryptedMounted`, `cipherPopulatedPlainEmpty`,
`loadEncryptedVolume`, `verifyBindMounts`, `encExecViaPlugin`, `awaitKeyringUnlockViaPlugin` — is
gone from `charly/`. The skill also quoted an error message that appears nowhere in the codebase,
and named a test file (`charly/enc_resolve_mount_test.go`) that does not exist.

Every claim is re-derived from the live tree and re-pointed at where the code now lives:

- `sdk/deploykit/enc_probe.go` — the probe and plan surface (`EncPlanFor`, `LoadEncryptedVolume`,
  `EncStatus`, `VerifyBindMounts`, `CipherPopulatedPlainEmpty`, `FuseAllowOtherEnabled`,
  `AskPassword`).
- `sdk/deploykit/enc_passphrase.go` — the resolution orchestration (`ResolveEncPassphraseForMount`
  and its `usesWaitingBackend` split, `EncNotStoredError`, `RetryUnavailable`, and the exported
  `EncMountDeadline` / `EncMountPollPeriod` that the skill had as lowercase in-core variables).
- `candy/plugin-pod/enc_cmd.go` — the `charly config status|mount|unmount|passwd` leaf bodies,
  including the all-mounted fast path and the injected keyring-unlock waiter.
- `candy/plugin-enc/enc.go` — the gocryptfs shelling, unchanged and already correctly described.

The quoted error is now the real `EncNotStoredError` text, the test reference is
`sdk/deploykit/enc_passphrase_test.go`, and its sub-case count is re-derived from the function
rather than carried over.

One internal contradiction fell out of this. The systemd source-classification list said `locked`
retries to a deadline, while "Event-driven keyring waiting" fifteen lines below said the wait is
unbounded. The code takes the unbounded branch whenever an unlock waiter is wired, which the
systemd path always does; the list now says so, and names the degraded no-waiter case rather than
implying it is the only one.

`/charly-core:charly-config`, `/charly-core:deploy`, `/charly-core:start` and the
`/charly-internals:go` source map each repeated part of the same stale claim. Fixed in the same
