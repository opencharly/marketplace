## Summary

The watcher family (`gh_watch.sh`, `pr_watch_many.sh`, `pr_state_watch.sh`, `_watch_common.sh` — the harness-independent `.sh` tools) exhausted the account's shared **5000/hr** core API budget with repeated fast/stacked polls and contributed to host load. This PR makes the arithmetic safe: a **60s poll floor**, **ONE batched GraphQL request per poll for the whole item list**, **skip-unchanged work**, and a **hard rate-limit abort**.

### The measured budget (R1) — measured, not asserted

- Defaults were **30s** (`gh_watch.sh`) / **20s** (`pr_watch_many.sh`) / **15s** (`pr_state_watch.sh`), each with a **minimum of 1s**.
- `gh_watch.sh`'s **`snapshot()`** issued **6 REST calls per ITEM per poll** (a `/pulls` type probe, `/issues` state, `/pulls` merged, `/issues/comments`, a per-item `gh run list`, and `/issues` updated_at — counted from the shipped source).
- Over **5 items** that is **30 calls per poll**: at `gh_watch.sh`'s own old **30s** default (2 polls/min) `6 × 5 × 2 = 3600/hr` (72% of the budget for ONE watcher), and at a then-reachable **20s** cadence `6 × 5 × 3 = 5400/hr` (**OVER budget**). Repeated fast/stacked polls produced **HTTP 403** and dead watchers.

### What changed

1. **60s default + `POLL_FLOOR=60`** in all three scripts. A sub-60s `--interval` is **REFUSED at parse time (exit 5)**; the only override is the explicit, tests-only `ALLOW_FAST_POLL=1`.
2. **One batched GraphQL poll** (`graphql_batch`) for `gh_watch.sh`: `issueOrPullRequest(number:)` serves BOTH PRs and issues, so a whole batch is ONE aliased query. **calls-per-poll = 1 request for N items.**
3. **Skip unchanged work**: the DELTA gates themselves do it — `comment` fires only on a changed comment count (`cc != pcc`), `verdict` only on a changed run id (`v != pv`). STATE events (`merged`/`closed`/`stall`) fire from the baseline by design and are never skipped; the batched poll itself is never skipped.
4. **Hard rate-limit abort**: any rate-limit signal — HTTP **403/429**, a zero remaining quota, or a GraphQL **`RATE_LIMIT`** body — prints a **`FATAL`** naming the reset time and exits **7**. Never a retry.
5. **Rate guard**: **`watch_rate_zero_abort`** is the ONE shared zero-quota guard (reached by both `watch_rate_gate` and `pr_state_watch.sh`); below `WATCH_RATE_MIN` back off the interval by `WATCH_RATE_BACKOFF_FACTOR` (default 2, capped 600s).

## How tested

### calls-per-poll: before → after (measured LIVE with a call-counting `gh` wrapper)

A wrapper logs every `gh` invocation then execs the real `gh`. A sleep hook TERMs the watcher after the FIRST sleep, so the run is exactly **seed + one poll** (deterministic two rounds), and `ALLOW_FAST_POLL=1` supplies the tests-only escape hatch:

```console
$ GHCOUNT_LOG=o.log ALLOW_FAST_POLL=1 <orig>/gh_watch.sh --events comment --interval 2 --timeout 20 \
    opencharly/marketplace#370 opencharly/marketplace#371 opencharly/marketplace#352 \
    opencharly/layer-charly-internals#60 opencharly/layer-charly-internals#56 opencharly/charly#714
$ wc -l < o.log
73
$ grep -c 'run list' o.log
12                       # 6 items x 2 rounds (seed + 1 poll)

$ GHCOUNT_LOG=n.log ALLOW_FAST_POLL=1 scripts/gh_watch.sh --events comment --interval 2 --timeout 20 <same 6 items>
$ wc -l < n.log
3
$ grep -c 'api graphql' n.log
2          # 1 seed + 1 poll  (billable)
$ grep -c 'rate_limit' n.log
1          # FREE endpoint — not billed
```

**The old 73 reconciles exactly with the 6-per-item rate:** `(73 − 1 free /rate_limit) ÷ (6 items × 2 rounds) = 6/item/poll`. **Per poll for N items:** old = **6 × N** REST calls; new = **1** GraphQL request (independent of N). The earlier draft's "~5" was wrong; corrected to the source-read 6.
