# 2026.241.1633 — feat: refresh the refs list automatically instead of by hand

## Summary of changes

Phase E of the candy de-submodule cutover. `candy/charly-marketplace/charly.yml` is the **one**
generation input, and every one of its **176** entries is a hand-written CalVer pin.

Hand-written pins go stale **silently**: the corpus keeps building, the drift gate stays green, and
the published skill is simply an old one. That is exactly the failure this cutover removed for a
single charly CI pin — and 176 hand-maintained pins are the same failure with more surface.

| Added | |
|---|---|
| `scripts/refresh-refs.sh` | resolves each pinned repo's newest CalVer tag and rewrites the pin. Does **not** regenerate, does **not** commit — safe to run and read. `REFRESH_DRY_RUN=1` reports without writing. |
| `.github/workflows/refresh.yml` | nightly 04:41 UTC (after the umbrella's 03:17 `sync`) + `workflow_dispatch`: bump → regenerate → open a PR when anything moved. Skips when a refresh PR is already open. |

It **regenerates as well as bumping**, which the umbrella's `sync.yml` does not need to: a refs bump
that did not carry its regenerated corpus would trip `deploy.yml`'s fail-closed drift gate on the
very next run.

### Two details that would be defects if got wrong

**Tags are compared numerically.** `gh api …/tags` is *push-ordered*, so a tag backfilled onto an
older commit would look newest — and lexicographically `"v2026.241.1605"` sorts **below**
`"v2026.241.936"`. The sort is `-t. -k1.2,1n -k2,2n -k3,3n`, verified on that exact pair:

```
$ printf 'v2026.241.936\nv2026.241.1605\nv2026.241.99\n' | sort -t. -k1.2,1n -k2,2n -k3,3n | tail -1
v2026.241.1605
```

**The rewrite anchors on the full old pin** (path *and* tag), so a repo whose name is a prefix of
another cannot be corrupted, and the optional `/candy/<name>` subpath that plugin repos carry is
preserved verbatim.

### What this PR deliberately does NOT do

It adds **only** the script and the workflow. The refs list and the corpus are left untouched — the
first refresh is the workflow's own job, and bundling a 40-pin content move into the change that
introduces the automation would make both harder to review.

```
$ git show --stat HEAD
 .github/workflows/refresh.yml | 183 ++++++++++++
 scripts/refresh-refs.sh       |  65 ++++
 2 files changed, 248 insertions(+)
```

### On review of the content it will publish

The content in these PRs is **not** unreviewed: each pinned repo validated its own change through
its own `pr-validator` before tagging. This republishes what those repos already landed; what it
removes is the human step of *noticing* that they did.
