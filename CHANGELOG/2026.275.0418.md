# 2026.275.0418 — fix(pr_state_watch): a queued re-run of the required workflow is PENDING, not BLOCKED

## Summary

`scripts/pr_state_watch.sh` could name the **wrong terminal state** three ways. All three have one cause: it classified from a **proxy** for the truth instead of from the artifact that carries it.

**1. A queued re-run read as a stale BLOCK** (this is #403). Measured on opencharly/docs#142: the watcher was armed after the REST re-run of run `36933867704` and exited at once with `BLOCKED verdict BLOCK at head 041625863`; attempt 2 started at 22:20:17Z and its check run began at 22:20:21Z, both **after** the watcher had exited. That attempt passed and the PR merged.

- *Cause:* the classifier read only `commits/<head>/check-runs`, which until the re-run's job starts still shows the previous attempt's FAILURE; a queued run has no check run, so nothing marked it in flight.
- *Fix:* before calling a red check terminal the script reads `actions/runs?head_sha=<head>`; an unfinished run of the required workflow makes the verdict PENDING.
- The workflow file defaults to `org-wide-pr-validator-required.yml`, overridable with `PR_STATE_REQUIRED_WORKFLOW`, mirroring the existing `PR_STATE_REQUIRED_CHECK`.

**2. A red check with NO review verdict read as a BLOCK.** The class is **not in the check run**: BLOCK and INCONCLUSIVE both conclude `failure`, and `output.title` / `output.summary` are **empty for BLOCK, INCONCLUSIVE and PASS alike** (measured on marketplace#405 — `null` / `""` — and on .github#157). The one artifact that carries the class is the gate's own PR comment, whose heading is `## Review — BLOCK` or `## validator INCONCLUSIVE — …`.

- *Fix:* the script reads that heading before it calls a red check a BLOCK. `INCONCLUSIVE` now stops with **exit 8** and says there is no finding to fix (per the skill this class goes to the operator, not into a fix loop); a real `BLOCK` still stops with exit 2.
- *New knob:* `PR_STATE_VALIDATOR_AUTHOR` (default `github-actions[bot]`) names the account whose comment is allowed to carry the class. The read is gated on the author because the gate's **own** comment is the only verdict: any other comment that happens to start with the same heading — a human quoting the verdict, a bot echoing it, a stale paste — must not be able to set the class for a fresh head. The read is gated on the author **and on the head the comment reviewed** — see 4 (`B18`): a verdict of that author left on an EARLIER head must not set this head's class either.
- This matters for cost, not tidiness: a false BLOCK starts a fix loop for a finding that does not exist, which is exactly what happened to me on #405 and .github#157.

**3. An older FAILURE beside a newer SUCCESS was invisible, and the branch that named it was unreachable.** The check-runs endpoint **defaults to `filter=latest`**, so a superseded attempt is never returned — the `POISON` branch ("newest SUCCESS, older FAILURE") could not fire, and its remedy text pointed at the per-repo `.github/workflows/pr-validator.yml` dedupe, which is **retired**.

- *Fix:* the read is now `filter=all`, and that state is `SUPERSEDED` — the script keeps polling and says so, because **the newer attempt settles the merge**: charly#750 merged at `03:15:37Z` carrying exactly that pair at one head. The unreachable `POISON` exit and its retired remedy are deleted (R5).

**4. A verdict from ANOTHER head could set this head's class** — `B18`, found by the review of this PR. The class read took the newest gate comment whose heading matched and never checked that it belonged to the current head, so a comment left on an earlier head could set the class for a fresh one; the guarantee claimed in 2 above was **not enforced by the code**.

- *Cause:* the read filtered on the author and the heading, but not on the head the comment reviewed.
- *Fix:* both comment shapes are now scoped by the signal each actually carries. The engine's verdict **names its head** (`Head SHA: `<sha>``), so it is accepted only when that sha **is** this head — deliberately **not** time-scoped, because a re-run at the same head legitimately leaves a verdict older than the newest attempt's run start. The workflow's own INCONCLUSIVE notice carries **no** head line (it names the run's class, not the head: its body is composed inside `pr-validator.yml`), so it is attributed by **time** instead — it is posted *during* the run it belongs to, so it must not predate this head's failed run.
- Nothing attributable is `UNKNOWN` → BLOCKED (exit 2), and the message says the verdicts on the thread name another head instead of claiming a BLOCK comment exists. Without the time arm a stale INCONCLUSIVE stopped the watcher at exit 8 ("no finding — escalate") on a fresh head whose own verdict was never read.

**5. The class read fetched only the FIRST page of comments** — found by the review of this PR. Its purpose is the **newest** verdict, and the API orders issue comments **oldest-first**, so on a thread longer than a page the newest verdict fell off the end of the fetch: the read then reported *no attributable verdict* for a head whose gate did produce one — the absent-verdict misclassification this PR removes, reintroduced through the read's own paging.

- *Fix:* the read **paginates**, exactly as the check-runs read does; since `gh --paginate` emits one JSON array per page, the `jq` slurps the pages and flattens them (`add // []`, so an empty fetch stays an empty list rather than `null`). New control `8m` stages a two-page fixture (100 fillers, then the verdict on page 2) and asserts both the **outcome** and the **call shape**; the control fails on the call shape, so `8m` discriminates rather than decorates.

**6. A wrapped message was reported as a doubled word** — the review read the `UNKNOWN` branch's two `echo` lines as rendering "…verdict on the **the** thread". The source has no doubled word: `grep -n 'the the' scripts/pr_state_watch.sh` matches nothing, and the pair reads "…on the" / "thread names another head…". The wrap is rewritten to "…on this" / "thread…" regardless, so no reading of the two `echo` lines can produce it.

Closes #403.
