The producer is **merged and tagged**: `opencharly/plugin-strata` tag `v2026.290.1034` → commit `c1279782` (verified with `git ls-remote --tags https://github.com/opencharly/plugin-strata`). Producer-first is satisfied; this PR is the consumer half.

**The ref names the candy directory, not the repo root, and that is deliberate.** The sibling `layer-*` pins use the `<repo>:<tag>` root form because a layer repo's root `charly.yml` *is* a candy manifest. `plugin-strata`'s root `charly.yml` is a project config instead (`repo:` + `discover:` only, no candy node), so it cannot resolve as a candy:

```
$ gh api "repos/opencharly/plugin-strata/contents/charly.yml?ref=v2026.290.1034" --jq .content | base64 -d
repo: github.com/opencharly/plugin-strata
discover:
    - path: candy
      recursive: true
```

Every other plugin repo in this same file is pinned the same way (`plugin-wl/candy/plugin-wl`, `plugin-qdrant/candy/plugin-qdrant`, …). The line was therefore added in the established plugin form, directly under the `layer-strata` pin.

The regenerated corpus adds exactly one skill page — `strata/skills/strata-cli/SKILL.md` — plus its entry in `.well-known/skills/index.json`. `strata-cli` is now **indexed** in the marketplace corpus.

**Round 2 — the round-1 finding, fixed at the source, with the gate re-run at zero warnings.** Round 1's gate evidence was produced with the main clone's dev binary, whose dev-build banner the body had dismissed as environmental. That was the right BLOCK: a warning in the pasted gate output is not environmental. The gate below now runs on a **fresh rebuild of the same pinned charly tag this repo's own `deploy.yml` builds** (`opencharly/charly` `v2026.277.1528`, `-ldflags "-X main.BuildCalVer=marketplace-ci"`), installed at an FHS packaged-install dir for the run, so no banner can appear. The corpus itself did not change: both gate runs are no-ops against the committed tree, as is CI's own drift gate on this head.

**RCA for the round-1 finding (R1).**

- **Mechanism:** `charly/plugin_loader.go:452` (`warnSkippedFHSPlugins`) emits the banner when the running binary is *not* at `/usr/bin` or `/usr/local/bin` **and** the host's `/usr/lib/charly/plugins` holds baked `.providers` files. This host has both — a packaged charly `2026.256.1316` at `/usr/bin` with 21 baked plugin manifests — so the main clone's `charly/bin/charly` warned. CI has no such directory, so its log carries no banner; the banner was a property of *where the local binary sat*, not of the generator.
- **Missed control:** my pre-push self-audit checked `rc`, artifact counts and `git status`, but never asserted the gate's **stderr was empty**; it reasoned about the banner instead of treating a non-empty stderr as a gate failure.
- **Blast radius:** the evidence only. The artifact was already correct — CI's drift gate passed on this same head with the same 495 artifacts.
- **Root fix:** run the gate with a fresh build of the pinned tag, installed at a packaged-install path, and count stderr bytes as part of the criterion (0 below). No code, corpus, or refs change was needed or made.
