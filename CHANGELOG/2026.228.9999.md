# 2026.228.9999 — `base_user` is the discriminator, not the OS name

Fixes a category error in the `distro:` guidance that `v2026.228.0456` shipped,
and it is the fourth wrong direction this one rule has taken.

## The category error

The rule ended: *"Anything else (fedora, centos, rocky, **cloud-user**) may omit
it."* `cloud-user` is an ACCOUNT name in a list of DISTRO names. An Arch cloud
image with `base_user: cloud-user` literally is "a cloud-user image", so the
sentence told its author to omit `distro:` — and `effectiveDistro` then returns
`""`, the guest drops out of `pacmanFamily`, and it takes cloud-init's bare
`pacman -S` into the D15 host-key race.

Worse, the same page already said the opposite in its long form, which names
"an Arch image whose account is not literally `arch`". Changed line versus
unchanged line, for the fourth time.

## Why the rule kept failing: it never named its own field

Every version stated the rule in terms of *guests* — "for a pacman-family guest
not literally named `arch`" — where "named" was glossed with distro ids, so it
parsed as the OS name while the parallel Alpine clause used "named" for the
account. Three different nouns, one actual field, and **the field was never
named**. It also dropped the load-bearing "and only from `base_user`", so
"infers ONLY arch and alpine" read as "Arch is auto-detected, full stop".

A guest with no `base_user` at all was covered by no sentence anywhere.

Every site now leads with the mechanism: `distro:` is read by the cloud-init renderer AND by the candy-selection path
and inferred **only from `base_user`**, only for `cloud_image`, and only for the
two literal values `arch` and `alpine` — so set it unless `base_user` is
literally one of those, **including when `base_user` is absent**.

## The four directions, for the record

| version | failure |
|---|---|
| "Omit for arch/fedora/debian/ubuntu" | false for debian/ubuntu — fail-dangerous |
| "every OTHER guest except fedora" | over-broad — fail-safe |
| "exactly two cases" | under-broad — fail-dangerous |
| "…(fedora, centos, rocky, cloud-user)" | category error — fail-dangerous |

Three of four erred toward breakage. The one that erred safe was the only one
filed non-blocking, and replacing it is what re-introduced the hazard.

## Root cause, still filed not fixed

`sdk/vmshared/cloud_init_render.go` names it: *"The proper long-term fix is
schema-level (distro required, or defaulted at entity-resolve time, for every
cloud_image source) — tracked separately, not attempted here."* Four rounds of
prose have now stood in for that constraint, and prose has no mechanism to stay
true when the table moves. Routed to the renderer's cutover with the
`composeRunCmd:483` raw-field asymmetry.

## Correction to this entry, and to four before it

A late round found a **fifth** reader of `Source.Distro`, outside the file every
previous version of this rule scoped itself to. `buildVmSyntheticBox`
(`candy/plugin-fleet/candy_select.go:180`) has **no source-kind gate** and uses
`distro:` — falling back to `base_user` — to pick the guest's package manager for
candy installation. Its own comment records the live RCA: a candy deploy onto a
debian guest ran `pacman` and failed with exit 127, and without a `DistroDef`,
`CompileSystemPackageSteps` silently compiled zero steps for every candy.

So the guidance "over-setting is inert — when in doubt, set it" was false and
**fail-dangerous**: it directed authors to put an unsure value into a field that
steers candy installation. It came from generalising one correctly-verified
consumer (bootstrap vocabulary lookups, genuinely unreachable from `cloud_image`)
to all consumers. **A verified claim about one consumer is not a claim about the
set of consumers**, and the enumeration that would have caught it is of *readers
of the field*, not of dispatches in one file.

That is the root cause of the whole series. Four rounds enumerated
`cloud_init_render.go` exhaustively and were each complete within it. The scope
was never questioned because it kept producing findings.
