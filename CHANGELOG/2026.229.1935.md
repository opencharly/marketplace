## Why this leg exists

`charly#289` merged `charly/main` into its branch after `charly#296` landed, so its source now
carries both cutovers' candy edits. The projection did not, and `marketplace drift` measured the gap
as a pair rather than a single number:

```
before   marketplace drift   EXIT 1 — 9 generated artifact(s) are stale
after    marketplace drift   EXIT 0 — clean (400 artifact(s) on disk match their sources)
```

The pair is the evidence. Either figure alone is a tree-state claim that goes stale the next time
anything merges; together they state what this leg *did*, which does not.

## The pruned orphan, named here rather than discovered from a tag

`ollama/skills/ollama-cli/SKILL.md` is **removed** by this regeneration. It carries a

**This is not an authored deletion.** `generate` collects header-carrying artifacts and removes any

**One of them was not stale — it was CORRECT, and a regeneration would have reverted it.**
`ollama-layer/SKILL.md` on `plugins/main` carried `Dependencies | supervisord`, matching
`candy/ollama`'s `require:`. `plugins#191` landed that correction from `charly@04b89ced` on branch
`feat/ollama-plugin`, **which was deleted afterwards**, so the fix reached the artifact and never
reached a source. Regenerating from the surviving source reintroduced `cuda` — and set it head-on
against `ollama/SKILL.md`, one directory away in this same diff, which states the candy carries no
`cuda` dependency.

The general form is the reusable part, and it inverts a rule this project otherwise relies on:

> **A projection can be MORE correct than its source, when the source-side fix landed on a branch
> that was later deleted.** Regeneration is then destructive rather than restorative, and *"the
> source is authoritative"* holds only while the source still exists.

The three false claims are now fixed in `candy/charly-ollama/charly.yml` and re-projected, so the
regenerated artifact matches what `main` already carried rather than reverting it. An earlier reading of this situation called all
three sourceless — a file-existence check reported as a provenance check. **Existence is not
provenance**, and the two answers differ for exactly two of the three. A first version of this entry
then attributed both survivors to one candy, which is the same error one level down: knowing a
declarer exists is not knowing which one it is.
