# 2026.241.1700 — fix: the refresh workflow opens its PR with the org bot token

## Summary of changes

The refresh workflow's first real run did everything correctly — 176 pins read, refs list bumped,
corpus regenerated, branch pushed — and died on the last step:

```
GraphQL: GitHub Actions is not permitted to create or approve pull requests
```

That restriction applies to `GITHUB_TOKEN`. **Enabling the switch it names is not the fix**: the
same switch also lets a workflow **approve** pull requests, which would let automation bypass
review, and it is off across this org deliberately.

## The org already solves this exact problem

`tag-on-merge` cannot write its CHANGELOG commit to a protected `main` with `GITHUB_TOKEN` either.
Its answer is a GitHub App token with a PAT fallback:

```yaml
- name: Create bot token (GitHub App)
  uses: actions/create-github-app-token@d72941d797fd3113feb6b93fd0dec494b13a2547
  with:
    app-id: ${{ secrets.CHARLY_AUTO_MERGE_APP_ID }}
    private-key: ${{ secrets.CHARLY_AUTO_MERGE_PRIVATE_KEY }}
```

This copies that pattern **verbatim** — same action, **pinned to the same SHA**, same
`CHARLY_BOT_TOKEN` fallback, same hard failure when neither secret is configured.

The workflow is now functional **without weakening review anywhere.**

## The error branch is rewritten too

It previously told a reader to enable `can_approve_pull_request_reviews`. That was advice to weaken
review in order to fix a token problem — the wrong instruction to leave in a file. It now points at
the app secrets and says explicitly **not** to reach for that switch.

The push-before-PR ordering is kept and stays commented: a token problem should cost a PR, not a
night's refresh, and the branch is already safe by the time the PR call runs.
