# 2026.228.0642 — the carrier test, corrected twice and swept this time

**This is a REGENERATION, not an authored edit.** `internals/agents/pr-validator.md` carries the
`GENERATED … DO NOT EDIT` banner; its source is `candy/charly-internals/charly.yml` in `charly`.

## Deciding whether a file is generated

The step-one rule flags files that MENTION a banner as well as files that CARRY one, and for two
rounds it named that problem without supplying a test. The criterion is now:

**Delete the file and regenerate. If it reappears, it is a carrier.** The question is whether the
generator PRODUCES that path, not whether its bytes currently differ. Verified both directions: an
in-sync generated agent spec reappears byte-identically; an authored CHANGELOG that merely quotes a
banner stays deleted.

**Do NOT decide it by whether the file moves in `git status`.** That answers a different question —
*is this carrier in sync* — and it fails in the direction that matters: an **in-sync carrier does
not move**, and in-sync is the normal state of a correct PR at validation time, so a movement test
returns *"not generated"* for exactly the file the rule protects. Movement can convict; its absence
proves nothing.

**Regeneration has two inputs, and only one of them is the artifact.** Standing at the wrong SOURCE
commit produced a full-file delete on a file that was perfectly in sync — indistinguishable from a
hand-edit. Reading the correct artifact ref does not save you; the source head has to be named, and
the page now gives an ordered way to resolve it and requires stating which was used.

## The procedure, not just the criterion

The test deletes a tracked file, so it runs in a **scratch worktree** that is torn down after —
never in a checkout anyone else is using. **Both generators run**: `marketplace generate` emits
`plugins/**` and `docs generate` emits `docs/**`, and running only the first makes every carrier in
the larger corpus answer *"not generated"*. The generator's **exit code is classified before the
file is read**, because a crash and a genuine mentioner both leave the file absent.

## STEP ONE now runs per-submodule

`git grep` does not cross a gitlink, so the superproject-relative form returned **zero hits** on
this repo's own files — indistinguishable from a clean tree, which is the silent-false-negative
direction the step exists to prevent. It is now `git -C <submodule> grep` with paths relative to
that repository.

## Banner positions and the census

**Positions are not reliably near the top**: this tree carries the banner at **24 distinct line
numbers, the furthest at 1214**. The guidance is *grep the whole file*; an earlier enumeration of
"typical" positions undersold its own case badly enough to invite a fixed window.

The census cites the **ref** it was counted at, not a date, and explains why its columns do not sum:

## Scope

**The files this leg carries are exactly those whose candy source this cutover changed.** That is
the invariant; it does not need a count, and a count is what kept going wrong.

Successive revisions of this entry claimed **twelve**, then **three**, then **zero** other drifting
files — three numbers for one question, each correct when taken and each falsified by the next
`update-branch`. Every one measured *how far behind this branch was*, not anything about this
repository. **A number that changes when you rebase was never describing the repo.** The invariant
above is stable under every one of those moves.

## This entry's own bookkeeping went wrong twice, in one command

The paragraph above was written a round earlier and **landed in the wrong file.** The edit selected
its target with `glob.glob('CHANGELOG/2026.228.06*.md')[0]` — a pattern that matched **two** entries,
this one and the already-merged `2026.228.0635.md`, with `[0]` picking whichever the filesystem
returned first. It returned the merged one.

Two defects from one line. **A landed, tagged release entry was rewritten** — `v2026.228.0635` names
that file, so after merge it would have read differently depending on which ref you asked, which is
the precise disease this cutover exists to cure, applied to the historical record. And the passage
deleted from it was a *"true when written, false when read"* narrative **carrying its own
justification for being kept** — while this same cutover ships the rule that a mechanical pass
*"deletes the retractions and leaves a page stripped of exactly the history that stops the claim
coming back."* **The deleted passage argued against its own deletion.** It is restored byte-identical
to `main` (blob `75f1f1f786a4`), and the invariant now sits here, where the false count actually was.

**Pin the path; never glob it.** A glob is a pattern that matched what it matched, and `[0]` over a
filesystem ordering is a choice nobody made. A convention check of the 198 entries on `main` found
five later edits, **all metadata repairs and none a narrative rewrite** — so the practice this
violated is real even though no rule states it.
