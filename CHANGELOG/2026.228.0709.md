# 2026.228.0709 — always set `distro:`, and the two tables that decide what to set

## What this release ships

**Always set `distro:`, as a bare id, to the vocabulary id whose package MANAGER
matches the guest.** The vocabulary `candy_select` resolves against is exactly
five: `arch`, `cachyos`, `debian`, `fedora`, `ubuntu`. There are no exceptions
and no omit branch. Concretely:

| guest | write |
|---|---|
| one of the five | its own id |
| manjaro, archarm, endeavouros | `arch` |
| rocky, almalinux | `fedora` — a **workaround**: it selects Fedora's DistroDef, `version: "43"` and COPR sections |
| a Ubuntu derivative | `ubuntu` |
| **alpine** | **`alpine`** — not a vocabulary member, but the init dispatch keys on `effectiveDistro`, so it is the only value reaching the OpenRC path. Candy installation stays unresolvable; losing packages is recoverable, losing the boot is not |
| openSUSE | nothing correct exists — zypper has no member and no near relative |

Two consumers read the field against **different sets**: `effectiveDistro` feeds
the cloud-init dispatches and accepts any string, inferring only `arch` and
`alpine` from `base_user` without checking the guest; `buildVmSyntheticBox`
resolves it against the five ids and, on a miss, leaves `img.Pkg` unset so candy
installation compiles zero steps silently. An id in the first set but not the
second is where that silent failure lives.

**Everything below is the history of how this rule was reached, including several
formulations that were retracted before shipping. Read it as history, not as
instructions.**


Supersedes the eight-id set, which **shipped in the plugins release `v2026.228.0547`** (`c00a4ca8`, verified on `plugins/main`) and in **no docs release** — the docs side went from the earlier gen-2 rule straight to this one. Two defects, both
introduced by fixes specified to close earlier ones, both at boundaries nobody
re-derived.

**F1 — the out-of-set proviso created a coverage gap.** A Fedora image with
`base_user: arch` matched no branch: not "guest is `arch`", not "id is in the
eight-id set", and the proviso excluded it from the omit branch. The natural
default — *not listed, so omit* — then gave `arch` from the account-only
inference and `pacman` on a DNF guest. The proviso correctly stopped that branch
giving a **wrong** answer; nothing then gave an answer at all.

**F2 — two instructions for one configuration.** "For any id outside that set,
omit" and "setting `distro: rocky` is the repair" both applied to a Rocky image
with a `cloud-user` account, in the same paragraph.

**Attribution correction.** F2 was a defect in the drafts *leading to* this entry; F1's mechanism — the out-of-set proviso — DID ship, in `v2026.228.0547`. An earlier draft of this entry opened by saying they superseded what `v2026.228.0547` shipped; that framing was wrong twice over. The eight-id set DID ship, in the plugins release `v2026.228.0547` (`c00a4ca8`), so that framing was wrong about the set as well — and on the merge commit `c00a4ca8` the shipped text says the **opposite** of the false remedy it was accused of carrying: *"`distro: rocky` fails exactly as the account did"*, that defect having been caught and fixed before the release merged. Corrected in place rather than by a trailing note, because this entry is not yet merged.

## The structural fix

Seven rounds of branch-by-branch patching, and each patch broke a boundary. The
eight-id set existed only to decide when omitting is safe, so reducing omission
to its two real cases removes the set, the third branch and the proviso together:

> **Set `distro:` to the guest's own id.** Omit it only when the guest is
> `arch` and `base_user` is literally `arch`, or the guest is `alpine` and
> `base_user` is literally `alpine` — the only two cases where the inference
> supplies the right value.

**Verified independently rather than adopted**, because the two defects above
were each specified by a reviewer and each broke an unre-derived boundary. Eight
representative guest/account pairs traced through all four cloud-init dispatches
plus `candy_select`; every one correct, including the two this closes —
fedora/arch now sets `fedora` and stays off the pacman path, and rocky/cloud-user
set `rocky` under that draft, which agreed with the repair sentence instead of contradicting
it.

**That verification found a boundary the proposal did not cover.** The value must
be a **bare id**: `ResolveDistro` strips at `:` but the cloud-init dispatches
compare the string exactly, so `distro: debian:13` yields `openssh` instead of
`openssh-server` and cloud-init hard-fails. No entity uses the tagged form today
and `ResolveDistro`'s own comment models it, so it is reachable.

## The pattern this closes

Every previous version failed at a *boundary between branches* rather than inside
one, and every fix repaired the branch in view. A rule with three branches and a
proviso has more boundaries than a reviewer re-derives; a rule with two cases and
no exception list has one.

## Correction — the two-case rule above was retracted before it shipped

The reviewer who proposed it retracted it, and the deciding data is the
`candy_select` vocabulary: exactly five ids, `{arch, cachyos, debian, fedora,
ubuntu}`. `manjaro`, `archarm`, `endeavouros` and `alpine` are all absent.

```
manjaro + base_user: arch
  SET manjaro -> not in the vocabulary -> img.Pkg unset -> zero candy packages
  OMIT        -> distroKey "arch" resolves -> works, same package family
```

So "set the guest's own id" is wrong for an Arch derivative shipping an `arch`
account. A second exception covered it at that stage — later dissolved, since manager-match subsumes it — and the five ids are named inline
because **vocabulary membership is the decision variable** — every earlier
version of this rule was undecidable for a reader who could not see the set.

**My own re-derivation missed this the same way the specification did.** I traced
`manjaro/arch` through the four cloud-init dispatches, saw `pac`, marked the row
correct and stopped — checking a consumer's *logic* and never its *table*. The
reviewer had written that exact sentence about its own error one message earlier.
The blind spot survived a change of position, which is the strongest evidence
that it belongs to the position rather than the person.

Two rows neither party had flagged fell out of the full derivation: `ubuntu` with
`base_user: ubuntu` needs the field SET, because the inference does not cover
`ubuntu`; and `alpine` with `base_user: alpine` leaves `candy_select`
unresolvable either way, since `alpine` is absent from the vocabulary too — a
product gap no VM entry can repair.

## J1 — deleting the omit branch cost Alpine its boot

Removing the omit branch removed the only route to the OpenRC init path.
`effectiveDistro` returns `Source.Distro` whenever it is non-empty, and the init
dispatch keys on `effectiveDistro`, not on the vocabulary. So the previous head
told an Alpine author to set one of the five vocabulary ids — none of which is
`alpine` — and any of them renders systemd onto a guest that has none.

**The trade that made: the version before cost Alpine its packages; this one cost
Alpine the whole VM.**

The fix is not to restore the omit branch. Setting `distro: alpine` reaches
OpenRC exactly as omitting does, and says so explicitly. It is not a vocabulary
member, so candy installation stays unresolvable — but losing the packages is
recoverable and losing the boot is not.

**The reasoning error is in how a branch gets deleted.** Dissolving a branch
removes its disclosure burden and its correct cases together. That omit branch
carried two things: an asymmetry that needed disclosing, and the only route to
OpenRC. Deleting it fixed the first by discarding the second. **"Can this branch
be deleted?" has to be asked as "what is this branch the only source of?"** — and
here the answer was not in the branch's own text; it was in a consumer that reads
a different field.

**And the sweep that authorised the deletion had the same blind spot as the
rule.** It reported "cases where OMIT beats ALWAYS-SET: openSUSE only". Alpine
scored as *no correct member*, so it dropped out of the comparison — while the
rule still directs the reader to set something, and setting anything is what
breaks it. **A case with no good option is not a case with no outcome.**

## And "resolves" is not "installs"

The same head claimed a near-relative id "makes candy installation resolve", and
treated that as the repair. `distro: fedora` on a Rocky guest resolves — to
Fedora's DistroDef, `version: "43"`, so candies' `fedora:43` sections apply and
the rpm templates reach for COPR, which is Fedora infrastructure. **The lookup
succeeding is not the install working.**

This is the checking rule from earlier in this entry applied one dereference
short: *check what a consumer's code does and what its data contains* got applied
to the key set and stopped there, without following the key to the definition it
returns. The blind spot moved down a level rather than closing.

## Correcting a claim already in released history

`docs`' copy of this entry merged as `CHANGELOG/2026.228.0635.md` (`3d111704`)
carrying the sentence *"the eight-id set — which no release ever shipped"*. **That
is false**, and it is now immutable: the eight-id set shipped in the plugins
release `v2026.228.0547` (`c00a4ca8`, on `plugins/main`). It never shipped on the
docs side, which is why the claim read as true when written from the docs leg —
the entry is shared between two repos whose release histories differ, and a
statement about "any release" cannot be true of both from one text.

**A second false claim is in the same released entry**, and naming only the first would leave it standing. `3d111704` also says *"F1 and F2 were defects in the drafts leading to this entry, **not in any released text**"*. F1's mechanism — the out-of-set proviso, *"provided `base_user` is neither literally `arch` nor literally `alpine`"* — is present verbatim in `c00a4ca8`, the commit `v2026.228.0547` tags. So F1 shipped; only F2's false remedy did not. These are two distinct claims, one about the eight-id set and one about F1/F2, not one claim in two wordings.

**Why the control missed it, which matters more than the omission.** The mechanical check adopted earlier — *extract every `<sha>` and `v<CalVer>` reference and resolve each before shipping* — was run against **this** entry, and it worked: it is what caught the dangling `charly@890f1683` — itself orphaned by the same squash, and cited only as the subject of a past defect rather than as a resolvable pointer provenance. It was not run against `3d111704`, the artifact this section is *about*. **A correction section has to be checked against the entry being corrected, not only the entry doing the correcting** — otherwise it can only ever be as complete as the recollection that wrote it, which is precisely the failure mode it exists to close.

**Recorded here rather than amended there**, per the same rule this cutover
applied to `v2026.228.0547` itself: a merged entry is immutable and a superseded
claim lives on as history, corrected by a later entry rather than edited away.

**And the mechanism is worth more than the correction.** Twice now, fixing a
