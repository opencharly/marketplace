# 2026.296.1533 — fix(refresh): resolve every pin in the pin's own scheme, and never backward

Head `024207d1c1a2ad88bfc5ea0bdac4e352c761f607` — 6 files, +424 −33. The daily refs refresh resolved every pin to the newest `vN.N.N` tag in the repo, sorting the components numerically, and the Go-module scheme's first component is the fixed major `0`, which sorts BELOW the year `2026`. The two Go-module pins in the refs list — `spec` and `sdk` — were therefore moved to a superproject tag: not a valid Go module version at all, and a tag from a month EARLIER than the pin it replaced. This PR replaces the resolver with one that resolves in the scheme the pin already carries, refuses to move a pin backward, proves that decision with a suite wired into the repo's own CI gate, and makes the workflow's prose say what the run actually does. The validator's review round on this PR named two non-blocking observations: the resolver's unused second input form is FIXED in the round's commit, and the scheme-detection remark is REBUTTED with the code.

## Summary

**The defect.** `scripts/refresh-refs.sh` took every `vN.N.N` tag in a repo, filtered them with a pattern that accepts BOTH tag schemes this org uses, and took the numerically greatest. `spec` and `sdk` publish both schemes — the superproject's `v<YYYY>.<DDD>.<HHMM>` and the Go module's `v0.<YYYYDDD>.<HHMM>` — so the superproject tag always won. The refs list states the contract in prose right above the two pins it breaks, and the code that rewrote those pins never read it. opencharly/marketplace#553 carries the corruption, and the validator BLOCKed it on exactly this.

**The fix, in three parts.**

1. **One resolver, in the pin's own scheme.** `scripts/resolve_pin_tag.py` is the tag resolver in this repo — there is no second copy. It reads the scheme from the pin the list already carries (the same component count, and the same character widths for the first two components), keeps only the candidates in that scheme, and picks the newest of them by VERSION, numerically. `scripts/refresh-refs.sh` calls it and no longer sorts tags itself.
2. **A pin never moves backward.** A repo whose newest tag in the pin's scheme is older than the pin leaves the pin alone; the run reports it as UNRESOLVED with the reason, so the pin stays where it is and the run says why.
3. **The control that missed it.** `scripts/refresh_refs_test.sh` drives the SHIPPED script against fixture tag lists and asserts the decisions — including the two that were wrong — with two RED ARMS that each turn the suite red by mutating a copy of the resolver. The repo's own CI gate runs it, so a broken resolver fails in seconds instead of corrupting a pin silently.

The workflow's prose and `AGENTS.md` now say "the pin's own scheme" where they said "its repo's newest CalVer tag".

**The review round.** The fresh `charly/pr-validator` reviewed this PR and PASSed it, naming two non-blocking observations. The second one is a real loose end and it is FIXED: the resolver's `--tags <file>` option had no caller at all — `scripts/refresh-refs.sh` feeds the repo's tags on stdin, and the suite drives that same shipped script — and an input form nobody uses is dead surface. The round's commit removes it, and the resolver now reads the tag list from stdin, which is what its one caller does. The first observation is a misreading of the code and it is REBUTTED with the code: the scheme's widths are read FROM THE PIN, never assumed about a repo's tag list. `scheme_key()` returns the tag's own component count and the widths of its own first two components, and a candidate is eligible only when the CANDIDATE's widths match the PIN's. A repo that published an unpadded variant would simply not be eligible, and its pin would be reported UNRESOLVED rather than moved.
