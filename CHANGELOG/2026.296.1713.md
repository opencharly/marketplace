# 2026.296.1713 — fix(refresh): stage the run's work before the report snapshots it

Head `daa99a1321e7cbdcdfa11404d6c45a650e65e7db` — 3 files, +492 −4. The daily refs refresh publishes its report under a legend that defines exactly three codes — `A` added, `D` removed, `M` modified — but the snapshot that report is built from was taken about two hundred lines BEFORE the run staged its work, so every file the run produced was still untracked at that moment and read `??`: a code the legend does not define, and a code the commit does not carry. This PR stages once, before the snapshot, and adds the suite that proves the report's codes are the commit's codes. This round makes that suite itself unfakeable: a red arm that goes undetected now makes the PROCESS exit non-zero.

## Summary

**The defect (unchanged by this round).** `.github/workflows/refresh.yml` took the report's status snapshot at the top of the "Open the refresh PR" step and staged the run's work about two hundred lines later, just before the commit. Everything the run produced between those two points was therefore untracked at the moment the report was written, and a brand-new generated file — a new skill entity under a new directory — read `??` in the pasted status block, under a legend that says the codes are `A`, `D` and `M`. The three counters were computed from the same block, and the added-counter accepted `^??` as well as `^A `, so the file count was right: the report was precise about the wrong thing. The fresh `charly/pr-validator` named it on opencharly/marketplace#557 — the refresh PR that carried it — and opencharly/marketplace#558 carries this defect's own record. This PR is that finding, fixed.

**What this round changes.** The validator BLOCKed the first push on three findings, all three of them in the suite that was supposed to prove the fix. They are fixed here, and each fix goes into the control that missed the defect, not only into the assertion:

1. **The suite could not fail.** `SHIP_FAILS` was captured BEFORE the arms ran, each arm's failure only bumped a counter that was reset afterwards, and the final gate tested only `SHIP_FAILS`. An arm that did not turn the suite red therefore printed `FAIL` and then printed `OK` and exited 0 — the exact "test that cannot fail" the suite claims to eliminate. The arms' failures now accumulate in `SELF_TEST_FAILS`, which is checked at the end, and the failure path is then proved AT THE PROCESS BOUNDARY: the suite re-runs ITSELF as a subprocess with its arms forced to be undetectable and requires a non-zero exit, with the child showing the arm's marker and no shipped-check failure, so the non-zero exit is attributable to the arm.
2. **The published body's counts were literals.** The body block was invoked with hardcoded `SKILLS=1 FILES=3 ADDED=1 REMOVED=1 MODIFIED=1`, so the check only proved that a template renders the integers it is handed. The suite now extracts the shipped counter lines out of the workflow, evaluates them on the fixture's status and refresh log, and hands THOSE values to the body block; a second run hands the body a different `ADDED` and requires the published body to change with it. The suite's own expectation is derived from the COMMIT — added is the commit's `A` entries, removed its `D` entries — and is not hard-coded.
3. **The pasted evidence was not reproducible.** `sort` is locale-dependent, so the order the report was compared in depended on the machine that ran the suite: the previous body of this PR pasted `D doomed.txt;M base.txt;? newdir/SKILL.md`, while a C-locale sort of the same three lines reads `? newdir/SKILL.md;D doomed.txt;M base.txt`. The suite now pins `LC_ALL=C`, so the comparison is byte-ordered and identical everywhere, and the evidence below is the C-locale order.

**Two further defects the reworking exposed and closed.** The fixture's own log files lived INSIDE the fixture repository, so the fixture staged and counted the suite's scaffolding: the counters read `1 1 6 4 1 1` instead of `1 1 3 1 1 1`. The shipped `ADDED` counter accepted `^??` as well as `^A `, which is exactly what let the counts agree with a PRE-STAGING tree — an untracked file was counted as an addition the commit did not carry — and that clause is now deleted, so the counts can only ever describe the commit. A third, smaller one: the comment above the counter block still described the deleted clause as current, so the prose contradicted the code it described; it now reads in the past tense and states what `ADDED` counts today.

**The CI wiring.** `.github/workflows/deploy.yml` now runs the suite with `--self-test`, so the red arms and the meta-arm are exercised on every run of the repo's own gate and not only on a developer's machine.
