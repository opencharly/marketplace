# 2026.243.0624 — fix(refresh): the generated PR body cannot pass A1 — name the files, drop the false footer

## Summary

**The nightly corpus refresh has been wedged since 2026-08-30.** `#254` was BLOCKed, and because
the workflow declines to run while any refresh PR is open, *nothing has reached the published
corpus since* — including skill fixes that had already merged and tagged in their owning repos.

Both blocking defects are in the PR body this workflow **emits**, so every future refresh would hit
them again. Re-running or hand-fixing `#254` would have cleared one night and left the mechanism
broken.

## The two defects

### 1. A1 — the body reported counts, never the files

```
echo "- **${FILES}** file(s) total"
```

`#254` said *"4 file(s) total"* and named two of them, leaving two regenerated corpus files
entirely unaccounted for. A count cannot be checked against a diff, and A1 requires every diff item
to appear in the body.

The body now prints `git status --porcelain` in full, and states what those files *are*: everything
outside `candy/charly-marketplace/charly.yml` is **regenerated output**, whose text the owning repo
authored and its own `pr-validator` gated before the tag existed. That is also the answer to
`#254`'s related block (*"the SKILL.md change is substantive content, not a pin refresh, and is
untested/undescribed"*) — it is neither authored nor reviewable here, and an edit made here would be
overwritten by the next generate.

### 2. The attribution footer claimed an attribution that does not exist

```
*Assisted-by: GitHub Actions opencharly/marketplace-refresh (fully tested and validated)*
```

A1 requires that line on an **AI-authored** body, in the exact form
`<Harness> <Provider Full Model Name> (<confidence>)`. This body is not AI-authored — it is emitted
by a fixed block in this workflow, with no model in the loop at any point — and
`opencharly/marketplace-refresh` is a repository, not a provider model. The line was therefore both
malformed *and* false.

Inventing a model-shaped string to satisfy the pattern would be exactly the false claim the rule
exists to prevent. The body now says plainly that it is machine-generated, why no footer applies,
and which file generated it.

## Not fixed here, on purpose

`#254`'s remaining block was **R4a — documentation routes around a defect**: the punktfunk skill
told readers to avoid scalar shorthand because of `charly#471`. That was a real defect, but in the
**owning** repo, and `charly#471` had already been fixed by `charly#473`. Fixed at source in
`plugin-punktfunk#11` (merged), verified by an A/B on an identical fixture — fails on
`charly v2026.242.0649`, passes on `main` — so a fresh refresh carries the corrected text instead of
republishing a workaround for a bug that no longer exists.

Nothing about that belonged in this repo, which is the point: a propagation PR cannot fix content it
merely mirrors.

**The workflow YAML parses** (`yaml.safe_load`), and the change is confined to the body-emitting
block — no change to pin resolution, generation, or the drift gate.

**The workflow was run from this branch before merging** — `workflow_dispatch` accepts a `ref`, so
this is not left as a claim:

Against `#254`'s *"4 file(s) total"* with two files unaccounted for, that is the defect closed.

**`#256` is nonetheless BLOCKed, and not by this change.** `workflow_dispatch` cuts the refresh
branch from whatever ref it runs on, so a branch-dispatched run bundles this very `refresh.yml` edit
in with the regenerated corpus — 25 files where the body accounts for 24, and an authored workflow
edit sitting inside a body that (correctly, for a normal run) says everything outside the refs list
is regenerated output. The validator caught exactly that, which is the system working.

It is an artifact of verifying before merge, not of the fix: a scheduled run, or a dispatch on
`main` after this lands, carries only the refs list and the corpus. `#256` is closed rather than
merged for that reason, and the clean refresh follows this PR.
