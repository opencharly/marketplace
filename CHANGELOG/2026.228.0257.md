# 2026.228.0257 — keep_images documents an image budget, because that is what it now is

Consumer half of `charly`'s retention Unit A. `keep_images: N` changed meaning in
`candy/plugin-clean/retention.go`: it used to rank **tag rows** and now budgets **two
ordinals** — the newest N *distinct images* per `ai.opencharly.box` group, and at most N
tags of each.

Two skills documented the old meaning and would have been false the moment that change
landed:

- `build/skills/build/SKILL.md` — *"keeping the newest N builds"* and
  *"newest CalVer tags to keep per image"*
- `core/skills/clean/SKILL.md` — *"all but the newest N per group are `podman rmi`'d"* and
  *"newest CalVer tags to keep per image"*

## Why this is not a follow-up

Measured on the producing branch's own fixture: with `keep_images: 3` and one image wearing
three tags plus three older distinct images, the new code retains **five tag rows** while
the shipped documentation says three. **That is a live doc-vs-reality divergence created by
the code change**, so it is blocking for that cutover rather than a tidy-up — R2's test is
whether shipping without it leaves the tree correct and the claim true, and it does not.

## Why a grep of the producing repo could never have found it

The changed symbol is `retentionRemovable` and the changed *claim* is "what `keep_images`
counts". A string sweep of `charly/` finds the first and is blind to the second, because the
claim lives in two other repositories under a word — `keep_images` — that the code change
does not rename. **A token search establishes absence-of-mention; only a claim-keyed sweep
across every repo that documents the behaviour establishes absence-of-divergence.** That is
the same blindness as a `git diff --name-only` reporting one filename for a gitlink bump: the
instrument answers, and the answer is about the wrong scope.

## What the corrected prose says

`keep_images: N` keeps the newest N distinct images per box **and at most N tags of each**.
Both halves are load-bearing and each alone regresses the other: ranking by tag row alone lets
one image wearing N tags consume the whole budget and starve the distinct images behind it;
ranking by image alone never reclaims a tag, so a content-stable image rebuilt many times
grows its tag rows without bound.

Reusing `N` on both axes is deliberate — distinct images bound **bytes**, tag rows bound
**metadata**, so the worst case is `N × N` metadata rows while bytes stay linear in `N`.
