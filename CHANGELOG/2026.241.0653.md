# 2026.241.0653 — fix: advance the CI charly pin so the setup-launcher fix reaches the published corpus

## Summary of changes

The `setup` launcher published on `main` is **broken for every consumer**: its second line is
`cd "$(dirname "$0")/charly"`, and this repo carries no `charly` submodule — the de-submodule
cutover removed it precisely because it dragged the whole charly repo into consumer fetch trees.
Run it from a fresh clone and it dies immediately:

```
$ ./setup --check
./setup: line 7: cd: ./charly: No such file or directory
```

charly#433 already fixed this, by bumping `plugin-marketplace` to `v2026.241.0124` (the
setup-launcher fix) — the generator that emits `setup` lives in that candy. The fix never
reached the published corpus because **this repo's CI pins charly at `v2026.240.2345`, which
predates #433**. So `marketplace generate` in CI kept building the OLD generator, kept emitting
the OLD launcher, and the drift gate kept passing — the corpus is self-consistent with a stale
pin, which is exactly the failure mode a pin-based gate cannot see by itself.

Concrete edits:

- `.github/workflows/deploy.yml` — the CI-time charly pin `v2026.240.2345` → `v2026.241.0522`
  (the newest charly tag; it carries `plugin-marketplace:v2026.241.0124`, verified below).
- `setup` — the regenerated launcher, carried in the same commit as the pin that produces it,
  per the workflow's own contract ("a marketplace PR must bump the charly CI-time tag and carry
  the regenerated corpus"). It resolves the checkout as `${CHARLY_SRC:-$here/../charly}` (the
  umbrella sibling layout), fails with an actionable message when neither exists, and passes
  absolute `--root`/`--out` instead of relying on the deleted submodule's relative position.

`setup` is the ONLY artifact that changes: regenerating the whole corpus from the new pin
touches nothing else (405 artifacts verified as a no-op, output below).
