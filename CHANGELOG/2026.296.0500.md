# 2026.296.0500 — feat(corpus): report each recorded consumer's recorded pin's currency

## Summary

A corpus landing does not carry a consumer's leg. The corpus advances by producer-first landings; each consumer's pin is advanced by a MANUAL act in the consumer's own repo, one PR per consumer, after the corpus lands. Nothing in that chain asked whether a consumer's recorded pin was still current, so a corpus could land while the consumer kept publishing a projection of the corpus it had already replaced. The consumer's own drift gate cannot see it: it asks "does the committed content match what the PINNED inputs generate?", and the pinned corpus generates its own (older) pages perfectly.

This change is the producer-side half — the report fires when the CORPUS moves and asks the question the consumer-side drift gate cannot ask.

Closes #543.

- `scripts/consumer-currency.sh` (new) reads the README's `## Consumers` table — ONE record of the consumer set, so a consumer is added by adding a row and the record and the report cannot drift apart — reads each consumer's recorded pin over the public API (GET /repos/<owner>/<repo>/contents/<path> answers a submodule entry with the gitlink sha the consumer records; no clone, no checkout), and judges that pin against this repo's merged main with `git merge-base --is-ancestor`.
- The states are the PIN CONTRACT's (the umbrella's AGENTS.md, Part II rule 3): `cur`, `behind`, `not-on-the-served-line`, plus `undecidable` and `unreadable`. A corpus is squash-merged, so a consumer pin that is off the main line is a SQUASH-ADVANCE whose one remedy is the same as `behind`'s — the consumer re-pins to the tip. The report says exactly that, and it never calls such a pin a divergence.
- The report NEVER fails. A consumer that is behind is an advance available NOW, in that consumer's own repo; a report that could fail the build would be a gate, and this is not one. The remedy for a consumer that is behind is that consumer's own pin-bump PR.
- Two cases the report refuses to guess: a SHALLOW history cannot decide ancestry (`merge-base --is-ancestor` answers "not an ancestor" for a commit the clone does not have, which is indistinguishable from a real squash-advance), so the report says `undecidable` and the refresh workflow checks out the FULL history; and a consumer set that cannot be parsed yields a report that reads NOTHING, which the report says loudly on stderr.
- `scripts/consumer_currency_test.sh` (new) drives the report against fixtures — a real fixture repository with a real main line, a real side branch and a real shallow clone, and a stubbed `gh` at the GitHub boundary — and drives the refresh workflow's own wiring.
- `README.md` gains the `## Consumers` table and loses the install table's `Docs` row (a repo is not a harness, and one record is the point).
- `AGENTS.md` names the record and the report.
- `.github/workflows/refresh.yml` checks out the full history, runs the report UNCONDITIONALLY (a corpus landing that moved no refs still moved the corpus), writes the report into the job summary, and pastes it into the refresh PR's body.
- `.github/workflows/deploy.yml` runs the repo's own script tests before the heavy toolchain build, so a broken script fails in seconds.
