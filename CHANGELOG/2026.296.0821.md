**Why DIRECT, and not left to the closure.** `plugin-marketplace#41` showed a skill reached only
through another repo's pin publishes whatever tag a sibling happens to name — the body is decided by
a stranger's refresh. A direct entry here makes THIS list the authority (`resolve.go`,
`preferEntity` step 2). The same reasoning is already recorded in this file for `plugin-mise`,
`plugin-openclaw` and `plugin-media`.

**Why `v0.…` and not `v<YYYY.DDD.HHMM>`.** Both are Go modules. A Go module tag must be semver, and
`v<YYYY.DDD.HHMM>` is not (a leading-zero minor is invalid), so each repo mints its own release
under `v0.<YYYYDDD>.<HHMM with leading zeros stripped>` — the sdk-scheme requirement, not a
preference. Each pin is the tag that repo's own merge minted, verified against the remote:

```
$ git -C sdk  rev-parse --short v0.2026296.803   → 5c5ef19
$ git -C spec rev-parse --short v0.2026296.734   → 965b37f
```

**And each tagged tree actually carries what is being pinned** — a pin is worthless if the tag
predates the content:

```

$ for s in capabilities ovmf libvirt-renderer cloud-init-renderer generate-source local-infra skills; do
```
