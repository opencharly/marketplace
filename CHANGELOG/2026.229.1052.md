## The false mechanism claim

The page said the orphan scan **"keys on the GENERATED HEADER, not on the path"**, and that a
header-less file **"is invisible to drift wherever it sits"**. Read against `scanGenerated`, both
directions are wrong. It has three arms and only the first reads any file's bytes:

1. it walks `plugins/<family>/skills` and `.../agents`, collecting whatever carries the header;
2. it adds a fixed list of known paths — each family's `plugin.json`, `.codex-plugin/plugin.json`
   and `.mcp.json`, plus `marketplace.json`, `profiles.json`, `setup` — if they exist, header or
   not;
3. it takes every file under `.claude/hooks/` outright.

So the header decides only inside the walked trees, and a header-less file is invisible only when it
**also** sits outside the known paths and the hooks directory — which is exactly the condition under
which `plugins/README.md`, `CHANGELOG/`, `LICENSE` and the scripts survive regeneration, and exactly
what `prune.go`'s own comment states 25 lines above the function.

The sentence predates this cutover; the previous round made it worse by adding *"one banner line is
the whole detection surface"*, which is true only where the canary sits. It survived because it was
the **unchanged** part of a diff an author and two validators were reading for what changed — the
condition under which a false mechanism claim is hardest to see.

## A sixth, found in this PR's own added text

The provenance paragraph said *"the count is 400 in **both** clean runs"* while the transcript prints
that line in **three** — and the page said so itself, ninety lines below, in text this PR did not
touch. Now stated as *"all three clean runs — 1, 3 and 6"*, which reconciles with the later sentence
by naming rather than by agreement.

**The first version of this entry blamed a sweep that missed it, and the history refutes that.**
`git log -S "both clean runs"` over the candy source gives four commits, and the sentence goes
present → absent → present → absent:

| commit | names the runs | counts them |
|---|---|---|
| `027c91a` | `Runs 3 and 4` | `both clean runs` — correct at the time |
| `2b2293f` | `Runs 1, 3 and 6` | **absent — the rebuild deleted it** |
| `85ca95c` | `Runs 1, 3 and 6` | `both clean runs` — **re-imported** |

The six-run rebuild swept it completely. The stale count re-entered at `85ca95c`, this PR's own
first commit, pulled back out of the superseded four-run draft while writing the elision fix beside
it.

> **Prose re-imported from a superseded draft is not residue, and no sweep can find it.** A sweep
> looks for what SURVIVED an edit; this did not survive — it was re-introduced later, as freshly
> added text that reads as correct because it *was* correct in its original home. The instrument
> that catches it is the one that catches any new claim: check it against the artifact at the moment
> you write it, no matter how confident its provenance feels.

A count is not a claim about the world; it is a claim about an artifact in the same file, and the
artifact moved.
