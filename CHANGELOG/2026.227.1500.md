# 2026.227.1500 — git-workflow: three landing-mechanics lessons

Amends `internals/skills/git-workflow/references/branch-and-pr-loop.md` and
`references/multi-repo-coordination.md`, plus a cross-reference in
`tools/skills/docs-site/SKILL.md`. Generated from the `git-workflow-skill:`
entity in `candy/charly-internals/charly.yml` and the `skill:` entity in
`candy/docs-site/charly.yml`; never hand-edited.

Three lessons from real landings that had no home in the skill corpus and were
sitting in an operator's private memory, where no fresh validator or teammate can
read them. Each extends text that already exists rather than adding a section,
which is deliberate: all three are refinements of rules the skill already states,
and a parallel copy is the failure mode two of them are about.

**`gh pr update-branch` invalidates every pasted bed citation.** The delta
re-gate already tells a reader to re-run the cutover's primary beds when the
overlap is non-empty. What it did not say is that re-running is only half the
remedy. `update-branch` merges `main` into the branch, and that merge can pull a
new builder-chain input — a submodule gitlink advance, a candy change — into the
chain a bed's fixture image builds from; every result pasted before it then
describes a tree that is not the one being merged. Nothing in the re-gate
updates the artifacts that CITE the superseded run, and it is the CHANGELOG that
ships inside the commit the evaluator tags.

The scope rule that goes with it: **block on what gets tagged, report what gets
squashed away.** The CHANGELOG entry and the PR body are both durable — the
entry lands in the tagged tree, and a merged PR body stays public and quotable
long after the branch is deleted — so a superseded run directory in either is
blocking. An intermediate commit message is replaced by the evaluator's squash
message, so a stale citation there is reportable but not blocking. Generalized:
a claim-keyed sweep runs LAST, once the final tree exists, because a record
written alongside the change it describes is written before the tree its reader
will check it against. It cross-references the freshness surfaces in
`references/evidence-and-freshness.md` rather than restating them.

**The `docs` gitlink has a twin in candy config that no gitlink check can see.**
The forward-gitlink hazard is documented twice over — the per-path
descendant-wins check and the whole-tree comparison that supersedes it — and
both compare gitlinks. `candy/docs-site/charly.yml` records the same `docs` sha
twice as ordinary text (the `DOCS_REF` var and the `docs-site-pinned-commit`
check's literal matcher), which a merge resolves line-wise with no notion that
those strings name a commit. A recovery can therefore satisfy both gitlink
checks and still leave the candy pinned at the older commit: the same regression
one surface over, invisible to every instrument aimed at it. The two gates are
complementary and neither substitutes for the other — the gitlink checks catch a
gitlink that went backwards, `task docs:pin` catches the gitlink and the candy
pins disagreeing and passes silently when both regressed together — so a
recovery that touches the `docs` gitlink runs both.

**A change class must be decidable from the diff.** B2 grants a submodule
pointer-bump commit the class of the commits it points at. That grant has a
boundary nobody had written down, and B6a step 4 blocked only its `DOCS_REF`
instance. The boundary now sits with the grant: a gitlink is a pointer git
itself resolves inside the repo the PR is against, so the derivation is
certifiable without leaving the PR, while a sha inside a candy `var:` resolves
nowhere. Were "the referenced content is documentation" the test, the class
would be a property of a tree the PR does not contain and no validator could
rule on it from the PR. Any pin the diff cannot resolve behaves the same way,
and when the diff cannot decide, the class is the heavier one.

B6a step 4 gains the positive half it was missing: the re-pin's gate is
`charly box validate` plus `check-docs` — the `disposable: true` bed composing
the changed entity through `docs-site-app` — at `fully tested and validated`,
and a landing whose only "extra" is that re-pin has its whole gate silently
upgraded, because `DOCS_REF` is emitted as an ENV line above the clone step and
re-pinning it changes the emitted Containerfile.

`/charly-tools:docs-site` owns the pin contract and is where a reader stands when
they perform the re-pin, so its ordering-consequence paragraph gains a pointer at
the class rule. A pointer, not a copy: the rule keeps one owner.
