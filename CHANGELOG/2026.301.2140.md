## Summary

Head `12b1bdd2e52caf9d58a3998467491b2ad4f40a4b` — 11 files changed, 266 insertions(+), 210 deletions(-).

**The defect.** The corpus published the `build` family from ONE source: `layer-charly-build`'s INLINE manifest — a candy whose repo is **drained** of the skill bodies it names (the bodies moved to the repos that now own them). The refs list pinned that one drained repo, so:

- the corpus kept the **pre-BuildKit prose** — the retired `--podman-jobs` flag, the retired `engine.build` builder selector, a flag the owner deleted — that the six owners had already replaced; and
- the six repos that now own the fifteen build-family skills were reachable only through the **closure**, never named.

So the corpus published stale prose about knobs the contract had renamed, out of a repo that no longer contains the prose.

**The RCA.**

- **Mechanism** — the corpus is a PROJECTION: `charly marketplace generate` reads each pinned repo's `charly.yml` and copies the skill bodies it names. A repo that has been **drained** of its bodies still satisfies "is pinned", so the projection kept resolving to it and kept publishing its old text; the new owners were reachable only if the closure happened to carry them.
- **Missed control** — the refs list names **DIRECT** sources, and the resolution rule prefers a direct ref over a closure twin. Nothing flagged that a direct ref had been drained, so the stale text was republished on every regeneration.
- **Blast radius** — the whole `build` family: fifteen skills whose prose told agents to pass `--podman-jobs` (opencharly/plugin-box#66 renamed that flag to `--stage-parallelism`) and to select a build engine (`engine.build`), which the BuildKit cutover retired. Every harness that loads the corpus read that prose.
- **Root fix** — name the six owners DIRECTLY in the refs list and drop the drained repo's ref in the same commit. A dead pin is the same class of defect as the stale body it holds up.
