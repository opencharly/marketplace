# 2026.294.2106 — fix(skills): the layer-python pin catches up and the corpus generator adopts the pinned-tree reader

## Summary

Two halves of one defect move together, because either alone leaves the corpus disagreeing with the refs list:

- the `layer-python` pin advances `v2026.273.1820` → **`v2026.293.1922`** (the repo's newest tag, twenty days
  newer), and
- `tools/marketplace-cli` adopts **`plugin-marketplace v0.2026294.1612`** — the #40 reader that makes THIS
  repo's own pin the authority instead of a transitively-reached twin.

This closes opencharly/marketplace#523, and it is its own PR: it folds nothing from A12
(opencharly/opencharly#557) and touches no skill body.

**The mechanism, as this issue states it.** Before #40 the dedupe let the transitive twin win, so the committed
`languages/skills/python/SKILL.md` carried prose from a ref the refs list does not name, and the corpus was not
reproducible from the list. With the #40 reader the pin decides.

**The one clause I have to correct, because the measurement contradicts it.** This issue predicts that the
regeneration changes exactly one page. It changes **none**. The committed page's body already IS the newest
tag's body — 2080B / 2070 chars, which are the very numbers this issue records for the committed corpus:

```
$ python3 - <<'PY'   (body() strips the frontmatter and the GENERATED banner)
```

So the page change this issue predicts happens in exactly one window: **generator bumped to #40 while the pin is
still the old tag**. That window is the drift-gate trip the issue warns about, and bumping both halves together
avoids it instead of suffering it. What the change removes is real — a pin 20 days behind and a corpus generated
from a ref the list does not name — but the visible page churn is not.
