# 2026.217.1834 — the deploy and service skills learn the backend-name boot gate

The `deploy` and `service` skills taught the encrypted-volume boot gate with a stale
three-way framing: *"Secret Service backend … auto-starts after login; KeePass or no
backend … requires `charly start`."* Both halves are wrong against the shipped code and
against the `enc` skill's **Boot Behavior: Which Backend, and Why** section (2026.217.0813).

- **"KeePass" is not a secret backend.** A KeePass database is reached *through* the
  Secret Service (KeePassXC's FdoSecrets plugin); nothing in `secret_backend` is named
  `keePass`.
- **"no backend" auto-starts.** `secretBackendIsKeyring()`
  (`candy/plugin-deploy-pod/secrets_resolve.go`) tests membership of `{"keyring", "auto", ""}`,
  and unset/`auto` resolve to the keyring — so an encrypted-volume deploy with no backend
  configured *does* get `[Install] WantedBy=default.target` and starts at boot, suspending in
  `ExecStartPre=charly config mount` (`TimeoutStartSec=0`) until the keyring unlocks. Only
  `secret_backend: config` omits `WantedBy` and needs an explicit `charly start` — a security
  decision recorded at sdk#121 and shipped as `warnCleartextStorage` in charly#213: a
  passphrase in cleartext must not be auto-mounted, unattended, at every boot.

Both skills now state the gate as the backend name and defer the why to
`/charly-automation:enc` (R3 — one source of truth for the boot-behaviour text). This closes
the two stale-prose hits reported by the sdk non-keyring-quadlet session.

Change class: documentation-only (two skill files). Attribution: documentation reviewed.
