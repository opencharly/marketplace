# 2026.241.0108 — fix: bump the authoritative refs list with the CI tag (the MCP removal now reaches the corpus)

## Summary

Bumps the CI-time charly tag **and the authoritative refs list together**, and
carries the two corpus artifacts that follow. This is the first PR in this chain
where the `build` drift gate passes.

**Root cause of the failing build (R1).** `candy/charly-marketplace/charly.yml`
exists in two repos with different authority. `deploy.yml` copies **this repo's**
copy over the cloned charly's before generating — its own step comment says so:

> The marketplace checkout's `candy/charly-marketplace/charly.yml` is the
> AUTHORITATIVE refs list … copied OVER the charly checkout's copy before
> generating — the charly checkout only supplies the in-repo candy dirs, never
> the refs.

So that file, not `deploy.yml`'s `--branch` tag, decides which candy **versions**
the corpus is built from. The documented procedure ("bump the charly CI-time
tag") moves only the source charly. Both must move.

At the point the build first failed, this repo's list still pinned
`charly:v2026.240.0831` and
`pod-charly-hooks:v2026.239.1634` — the version **with** the stdio `github` MCP
server. So CI kept regenerating `internals/.mcp.json` and drifting the whole
`internals` plugin, while opencharly/charly's `skills:drift` reported `no drift`
(it validates against charly's non-authoritative copy). That is how
opencharly/charly#426's bump shipped with no effect.

**Scope, stated precisely:** the `.mcp.json` deletion and the description fix are
already on `main` (they landed with #234, whose `build` was red). This PR does
not re-delete them. What it does is make the refs list agree with the corpus, so
CI stops regenerating the removal **back** — turning a removal that only held
because it was committed by hand into one the gate actually verifies.

### What changed — all four files

| File | Change |
|---|---|
| `.github/workflows/deploy.yml` | charly CI tag `v2026.240.2158` → `v2026.240.2345` |
| `candy/charly-marketplace/charly.yml` | `charly` → `v2026.240.2345`; `pod-charly-hooks` → `v2026.240.2141`; `pod-selkies-core` → `v2026.240.2344` |
| `internals/skills/skills/SKILL.md` | +18 — the generated projection of opencharly/charly#427 (the plugin cache is commit-keyed, so refreshing a marketplace does not update an installed plugin) |
| `selkies/skills/selkies-core/SKILL.md` | regenerated at the new `pod-selkies-core` pin |

**The `pod-selkies-core` bump** closed the last stale artifact. The pinned
`v2026.239.1558` still describes `chrome-wrapper` polling for the `wayland-0`
socket; CI regenerated the newer wording where the service's `wait_for:` blocks
before Chrome execs — text that exists only in `v2026.240.2104`+. CI was
resolving a **newer** `pod-selkies-core` transitively than the top-level pin
named, while a local run resolved the pinned one. Pinning the top level to
`v2026.240.2344` makes both resolve the same content. Flagging for maintainers: a
transitive ref outranking an explicit top-level pin is its own hazard, and it is
what made this artifact drift invisibly.
