# 2026.216.1400 — three skill surfaces described `--repo` resolution as it was before it worked

`charly --repo <owner/repo> <word>` could not reach an out-of-process command
verb: `kong.Parse` freezes the grammar before `main()`'s post-parse chdir, so a
word living only in the `--repo` target was never registered. The fix
(opencharly/charly#207) resolves `--repo` in the pre-parse prescan and exempts a
`--repo` cache from the stale-binary guard. Three skill surfaces in this repo
still described the world before that change.

`internals/skills/go/references/source-map.md` published `projectDirPreParse`'s
resolution chain as `CHARLY_PROJECT_DIR` → `scanDirFlag` over `os.Args` → cwd —
omitting `--repo` / `CHARLY_PROJECT_REPO` entirely. The row now carries the full
chain, why the prescan must resolve it there rather than leaving it to the chdir,
that resolution is attempted only when the flag or env var is present so a bare
invocation never touches the network, and that an unresolvable spec falls through
to cwd so the LOCAL grammar survives.

`image/skills/image/SKILL.md` said all five project-selection paths are "resolved
by a single `os.Chdir(cli.Dir)` call". The chdir is still single; the RESOLUTION
is not — `--repo` also resolves in the prescan, and saying otherwise is exactly
the reading that made the original bug look impossible. Split into the two
statements.

`internals/skills/agents/references/parallel-bed-testing.md` described
`CheckBinaryFreshness` as uniformly per-tree. It now records the one exemption: a
`--repo` cache is skipped, because a cache matches the source-root detector but
git has just written every file in it, so its mtime always beats the binary and
the guard fired on every `charly --repo … <heavy verb>` — telling a packaged user
to rebuild from a tree their binary did not come from. Keyed on the tree, not the
flag, so it covers `CHARLY_PROJECT_REPO` and a plain `cd` into a cache too.
