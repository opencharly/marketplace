## The mechanism, corrected

The page claimed the orphan scan **"keys on the GENERATED HEADER, not on the path"**, and that a
header-less file is **"invisible to drift wherever it sits"**. Both directions are wrong.
`scanGenerated` has three arms and only the first reads any file's bytes:

1. it walks `plugins/<family>/skills` and `.../agents`, keeping what carries the header;
2. it adds a fixed list of known paths — each family's `plugin.json`, `.codex-plugin/plugin.json`
   and `.mcp.json`, plus `marketplace.json`, `profiles.json`, `setup` — on existence alone, header
   or not;
3. it takes every file under `.claude/hooks/` outright.

So the header decides only inside the walked trees, and a header-less file is invisible only when it
**also** sits outside the known paths and the hooks directory — which is what `prune.go`'s own
comment states, 25 lines above the function.

## The regeneration window

The projection-first ordering guarantees a period where `plugins/main` carries prose `charly/main`
cannot reproduce, and the number of open windows is the number of superproject legs that have not
landed. `marketplace generate` cannot detect it — it faithfully emits what the source it was given
projects.

**Your own leg's window is harmless; another leg's is not.** While no other leg has landed into your
base, an unscoped whole-tree regenerate is clean and is the strongest evidence available. Once
another leg's projection lands beneath you, that same check turns destructive: regenerating from a
source lacking their candy entities deletes and reverts their work while reporting success. Measured
here — regenerating this cutover's source against the updated base deletes
`ollama/skills/ollama-cli/SKILL.md` and reverts two more skills belonging to a third session's open
leg. **The trigger is the base moving under you, not the existence of a window.**
