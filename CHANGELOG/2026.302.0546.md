# 2026.302.0546 — fix(gate): the shared-gate check's failure message names both causes it cannot tell apart

## Summary

Head `f6154d9040a603901e6510f6b19fa3fabbed80c3` — 1 file changed, 21 insertions(+), 12 deletions(-).

The `charly/pr-validator` verdict on opencharly/marketplace#596 carried a minor non-blocking observation:

> The `bad` message "the gate has a second implementation" is imprecise for the "call simply removed" case; functionally the check still fails correctly.

**The mechanism.** The check observes ONE fact — the call to the shared gate is absent — and the message asserted a CAUSE it cannot know. Two different defects produce the same absent call: the call was deleted, or the workflow grew its own inline copy of the check. The message named the second, so a reader whose real defect was a deleted call was sent looking for a copy that was never there. The same wording stood in both call sites — the refresh-side check and the `E-CALLERS` check — as two hand-maintained copies of ONE rule, so the imprecision was in both.

**The fix.** ONE helper, `assert_shared_gate_caller`, is now the single implementation of that rule for BOTH callers (the refresh job and the `marketplace` workflow) — the two hand-maintained copies are deleted in the same cutover (R2) — and the failure message names BOTH causes the check cannot tell apart:

> either the call to the shared gate is missing, or the check has a second implementation here

It asserts nothing the check does not know. The check's behaviour is unchanged: it still goes RED whenever a caller does not call the shared gate, and the red arms still prove it. Both shapes are run against the shipped suite — the `marketplace` workflow with the shared gate copied inline, and the `marketplace` workflow with the call simply removed — and both go red with the same message.

**The proof that the change is what makes the difference.** The assertion *"the failure message names both causes"* is run against the shipped suite in two states: with this change (it finds the message) and with the file as it is on `origin/main` (it does not). The gate's own exit status is 1 in both states — the check fires either way, which is exactly what the validator's observation said — and only the MESSAGE differs.

Closes #597
