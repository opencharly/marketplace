# 2026.215.1601 — `/charly-internals:skills`: the replacement claim carries the removal's burden of proof

Adds a rule the docs-site cutover paid for four times.

## What the rule says

Correcting a false doc/skill/comment produces **two** claims — the deletion and the successor —
and both need evidence. The failure mode is applying rigor to the deletion and a plausible guess
to what replaces it: the false claim is gone, a new one ships in its place, and the sweep that
would have caught it has already run.

## Why it earned a section rather than a sentence

Four replacements written during one cutover were themselves false, across three repos. Two
corrected a stale `directory:` claim (charly, sdk); two corrected the cross-reference rewriter's
own documentation (plugins, both in the same file). They share a mistake, not a subject:

- "inline entries have no source directory of their own" — `ScanInlineCandy` is passed `rootDir`,
  and an inline candy's `SourceDir` always equals its declaring file's directory.
- "the branch fires for a remote or submodule-vendored candy" — `CandyCopySource` early-returns on
  `GetRemote()` as its first statement, so a remote candy never reaches that branch.
- "the 11 frontmatter references are published as plain subtitle text" — `firstLine` truncates the
  description to its first sentence; all 11 sit past the cut and are published nowhere.
- "3665 references … every reference is rewritten" — 3654 are rewritten; the count was taken
  whole-file and described as body-scope.

Every one shares a root cause: **measuring or reasoning at one scope, then describing another.**
Each was caught by a reviewer running the thing being described rather than reading the
description — which is the practical reason the rule is worth stating rather than assumed.

The section adds four rules: trace the successor before writing it (read the early returns above a
branch, read the emitter rather than the producer); state a partial enumeration as partial;
re-derive figures at the scope the sentence names, using the code's own matching rules where one
exists; and treat a correction as a new claim subject to the same gate as the original edit.

## Also in this release — `/charly-tools:docs-site` pins a commit, not a branch

The skill still said the docs-site candy "builds against the docs repo's `main`", contradicting
the candy and describing a design that was a correctness bug.

`var:` values are emitted as `ENV` above the plan steps, so a branch name leaves the clone
layer's cache key constant: the bed rebuilds whatever commit that layer first captured, forever.
That shipped, and **every run passed while proving stale content** until review caught it. The exact number is no longer traceable in-repo — `keep_check_runs: 3` has since pruned those runs — so it is stated as "every run" rather than a count nothing can check.
`DOCS_REF` is now an immutable commit, and the `| DOCS_REF | main |` row of the variable table —
the same claim in a different syntactic form, a few lines below the prose that corrects it — is
fixed with it. Missing that row on the first pass was a string-keyed sweep where R5 requires a
claim-keyed one.

The troubleshooting table's single row for a now-impossible error is replaced by four rows: two
for the new guards (`docs-site-pinned-commit` failing on a stale layer, `task docs:pin` failing on
drift) and two for the fetch failures that can actually occur, both probed against the real remote
rather than reasoned about:

| Error | Cause |
|---|---|
| `upload-pack: not our ref <sha>` | the commit is not reachable from any ref in the docs repo |
| `couldn't find remote ref <x>` | `DOCS_REF` is not a full 40-hex sha — a ref name, or an abbreviated sha, which `git fetch` rejects even when the commit exists |

The first replacement row written for this was itself wrong twice — it paired the ref-name error
with a sha condition, and gave the boundary as "not on `main`" when GitHub serves any commit
reachable from any ref (verified: a commit from a merged-and-deleted branch fetches fine). That
is the failure the section above codifies, committed in the same PR that adds it.
