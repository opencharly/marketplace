# 2026.301.1446 — fix(refresh): the body's elision covers BOTH per-ref progress shapes

## Summary

Head `29290dd9830e8fc28b45739fb0efffe0027c90f2` — the commit this PR pushes: **5 files changed, 810 insertions(+), 59 deletions(-)**

The daily corpus refresh has failed for five consecutive nights (2026-10-24 through 2026-10-28). It assembles a PR body of about 117 000 bytes, GitHub refuses it — `Body is too long`, the limit is 65 536 — and the published corpus is frozen at the 2026-10-23 run. Two mechanisms, both in `.github/workflows/refresh.yml`:

1. **The elision covered ONE of the generator's TWO per-ref progress shapes.** #413 (merged as #414) elided the literal `Downloading <ref>…` and added a byte-size assertion. The generator prints a second per-ref progress line, `charly: resolving <ref> (N resolved, M queued)`, from a different module (opencharly/sdk `candywalk/candywalk.go:208`; the first is opencharly/spec `refs/git.go:732`). That shape was pasted whole. On the 2026-10-28 run's own log — run 74, 2 278 lines, 179 835 bytes — the one-literal elision removed 72 601 bytes (890 lines) and left 107 234 bytes; with the body around it, the assembled body was 117 236 bytes, 1.8 times the cap.
2. **The size gate ran AFTER the push, and its message named the wrong shape.** It blamed the `Downloading …` lines — the one shape that WAS being elided — so for five consecutive days the error pointed the reader at the wrong thing.

This change fixes both.

- The elision is ONE implementation, `scripts/refresh-elide.sh`, with TWO DECLARED classes — both per-ref progress shapes, and the generator's own artifact-path list — and every other line pasted VERBATIM. A warning is the one thing that section exists to surface, so nothing outside the two declared classes is ever elided. The elision is measured, not assumed: the notice names each class's line count and byte count, and the count of lines actually shown.
- The size gate runs BEFORE the commit and the push, in full, and names the section that actually grew — the pasted generator block's bytes and every other section's bytes — instead of the one that was already being elided. When it fires, nothing is committed and nothing is pushed; the next run re-resolves every pin to its repo's newest tag and regenerates the corpus from that refs list, so the advance is deferred to the next run, not dropped.

On the same run-74 capture: **179 835 bytes in, 87 bytes shown**, and the assembled body is **8 650 bytes** of the 65 536 the cap allows.

Closes #451.
